🔌 연결 서버 계정 (ActivityPub · AT Protocol)

Claire 는 ActivityPub 서버(Actor · Inbox · HTTP 서명)나 AT Protocol PDS 를 직접 구현하지 않습니다. 각 테마는 기존 서버의 계정에 클라이언트로 접속하며, 타임라인 열람 · 정기 수집 · 부스트 · 발행은 모두 그 계정의 서버 API(Mastodon Client API · AT XRPC)를 Claire 서버 프록시로 호출합니다. 계정은 테마별로 격리됩니다.

ActivityPub 클라이언트 기능 기준: Mastodon 5.0 이상. 연합 클라이언트는 Mastodon 5.0 이상이 제공하는 클라이언트 기능을 모두 갖춥니다. Mastodon API 를 제공하는 서버라면 종류와 관계없이 연결할 수 있으며, 연결 시 GET /api/v2/instance 로 확인한 결과 서버가 제공하지 않는 기능만 비활성으로 표시합니다.

Mastodon 5.0 기준 클라이언트 기능 (연합 클라이언트 탭의 📋 기능 기준에서 직접 시연)
• 타임라인 · 탐색: 홈(실시간 스트리밍) · 로컬 · 연합 · 해시태그(팔로우) · 리스트 · 탐색(트렌드 게시물·해시태그·링크) · 통합 검색(원격 계정 확인) · 개인 메시지 · 좋아요 · 북마크
• 알림: 묶음 알림(좋아요·부스트·팔로우·인용·멘션) · 멘션만 보기 · 알림 요청 · 알림 정책
• 게시물 표시: 부스트한 사람 · 공개 범위 · 언어 · 열람 주의(CW) · 미디어 대체 텍스트 · 민감한 미디어 가림 · 투표 · 인용 게시물 · 수정 이력 · 번역 · 키워드 필터
• 게시물 동작: 답글 · 부스트 · 좋아요 · 북마크 · 인용(인용 허용 범위) · 고정 · 수정 · 삭제 후 다시 쓰기 · 대화 뮤트 · 신고
• 작성: 공개 범위 4종 · 언어 · CW · 투표 · 미디어(대체 텍스트·민감함) · 예약 게시
• 계정 · 관계 · 안전: 프로필(필드·고정 게시물·추천 해시태그) · 팔로우(새 글 알림·부스트 표시) · 개인 메모 · 리스트 · 뮤트 · 차단 · 도메인 차단 · 필터 관리
프로토콜 서버 · 소프트웨어 계정 인증 방식 scope 발행 관리

새 계정 연결은 연합 클라이언트 탭의 🔌 계정 연결에서 OAuth 승인 흐름으로 진행합니다. 연결 해제 시 서버 토큰도 함께 폐기합니다.

🛡️ 연결 계정 보안 원칙
• 토큰 서버 보관: 접근 토큰은 테마 DB(syndication_accounts)에 암호화 저장되며 브라우저로 전달하지 않습니다. CSP default-src 'self' 아래에서 모든 원격 호출은 Claire 서버 프록시를 거칩니다.
• 최소 scope: ActivityPub 은 read + 필요한 write:* 세부 scope 만, AT 는 OAuth(PAR + DPoP) 우선 · 앱 비밀번호는 호환 모드입니다. 비공개 테마는 read 전용으로만 연결합니다.
• 폐기: 연결 해제 시 POST /oauth/revoke(Mastodon) 또는 AT OAuth 토큰 폐기 · com.atproto.server.deleteSession 을 호출합니다.
• 서버 예절: 응답의 레이트 리밋 헤더를 준수하고 429/5xx 에는 지수 백오프로 재시도하며, 사용자가 입력한 서버 주소도 SSRF 가드를 통과해야 합니다.

📡 정기 수집 대상 및 카테고리 폴더 관리

선택한 테마 DB의 RSS/Atom 피드와, 연결 계정을 경유해 수집하는 ActivityPub · AT Protocol 대상(계정 · 해시태그 · 리스트 · 커스텀 피드)과 수집 주기를 관리합니다.

프로토콜 카테고리 폴더 수집 대상 이름 식별자 / 피드 URI 경유 계정 수집 주기 상태

🏷️ 수집 태그 → 적재 시 엔티티 승격 및 생성 정책 (Tags → Ingested Entities)

수집 시점의 피드 태그는 외부 메타데이터이며, 온톨로지 엔티티는 '적재(Ingestion)'가 수행될 때 비로소 생성 및 해결됩니다. 클레어바이블 지식 그래프에서 태그는 곧 엔티티(entities 노드)이므로, RSS <category>, Atom term, ActivityPub Hashtag, AT Protocol facets에서 수집된 외부 태그는 적재 시점에 프로젝트 적재 정책([태그] 메타데이터 섹션 주입 및 Entity Resolution)에 따라 테마 DB의 엔티티로 정규화·생성·연결됩니다.

RSS/Atom/AP/AT 원문이 제시한 태그를 테마 DB의 기존 entities.norm_name 및 aliases와 대조해 동일 엔티티로 연결합니다.
테마 DB에 아직 없는 태그라도 적재 시 온톨로지 엔티티 후보로 생성하여 지식 그래프 탐색 및 추후 병합(Dedup) 대상에 포함합니다.
[[KV Cache]] → #KVCache 형태로 변환하여 연합우주 검색성을 높입니다.
RSS 피드에서 흔히 유입되는 의미 없는 일반 분류어(예: uncategorized, general)가 온톨로지 엔티티를 오염시키지 않도록 적재 전 필터링합니다.
프로토콜별 태그 수집 필드 ↔ Claire 엔티티 매핑 명세 보기
• RSS 2.0 / Atom 1.0: <category>, <dc:subject> → 적재 원문 상단 [태그] 섹션 병합 → entities 정규화
• ActivityPub (AP): object.tag[type="Hashtag"].name (# 접두사 제거 후 정규화) → entities 정규화
• AT Protocol: app.bsky.richtext.facet#tag 및 레코드 tags[] → entities 정규화
• 리더 하단 태그 바 조작: 미적재 원문 상태에서는 🏷️ 수집 태그 (#Tag)로 관리되며, 적재하기 실행 시 온톨로지 엔티티 [[Entity]]로 승격되어 적재 본문에 귀속됩니다.

⚡ 테마 DB 기반 오거나이즈 · 자동 적재 규칙

정기 수집된 컨텐트를 테마 SQLite DB의 엔티티 연관도(Affinity Score)로 채점하고, 임계치 이상인 항목을 프로젝트 적재 파이프라인으로 자동 전달합니다.

피드의 자동 적재 옵션이 켜져 있을 때, 엔티티·규칙 합산 점수가 이 기준 이상이면 즉시 POST /ingest 적재 큐로 전달합니다.

🔁 연결 계정 부스트·인용 발행 및 적재 본문 발행 정책

RSS/ATOM · ActivityPub · AT 항목 모두 부스트/인용 발행(Boost / Quote)과 적재 발행(Ingested Body Publish)을 지원합니다. 발행은 Claire 자체 액터가 아니라 연결 계정의 서버 API(POST /api/v1/statuses · com.atproto.repo.createRecord)로 수행되며, 부스트는 같은 프로토콜 계정에서만 가능합니다.

현재 테마 발행 연결 계정 발행 권한(write scope)이 있는 연결 계정으로만 외부 발행 · 부스트할 수 있습니다.
RSS / ATOM 항목 발행 대화상자 기본 모드 RSS/ATOM 기사에서 발행 버튼을 눌렀을 때 기본으로 선택될 발행 모드를 지정합니다 (대화상자 안에서 언제든 두 모드 간 전환 가능).
ActivityPub 항목 발행 대화상자 기본 모드 연결 계정 경유로 수집한 Fediverse 게시물에서 발행 버튼을 눌렀을 때 기본으로 선택될 모드입니다.
AT Protocol 항목 발행 대화상자 기본 모드 Bluesky 등 AT 게시물에서 발행 버튼을 눌렀을 때 기본으로 선택될 모드입니다.
연합우주 팔로워가 클릭 시 Claire의 정제된 지식 그래프 공유 문서 뷰어로 이동할 수 있도록 합니다.
사용 가능 치환자: {{title}}, {{url}}, {{author}}, {{hashtags}}

👥 사용자 간 발행 본문 공유 제안 · 미구현

사용자별 워크스페이스(EXTERNAL_IDP_AND_PER_USER_WORKSPACE_DESIGN.md §4.7)에서, 공개 테마의 적재 발행은 공개 사본만 인스턴스 공용 발행 색인(data/shared/publications.db)에 올라갑니다. 같은 Claire 의 다른 사용자는 연합 클라이언트 · 지식베이스 탭의 👥 다른 사용자 발행 본문에서 이를 보고 자기 연결 계정으로 발행할 수 있습니다. 워크스페이스 DB 는 서로 열지 않습니다.

끄면 공용 색인에 올리지 않습니다. 연합우주에 이미 발행한 게시물과 공개 공유 링크는 그대로입니다.
항상 허용되는 재사용 공개 발행이므로 부스트(reblog · repost)와 링크 공유는 막을 수 없습니다.
🔁 부스트 · ✎ 링크 공유
연합우주에서는 원 게시물의 인용 허용 범위(quote_approval_policy)도 함께 적용됩니다.
가져온 사본은 그 사용자의 수집 원문이 되고, 다시 발행할 때는 원문 링크와 작성자 표시가 붙습니다.
목록과 공유 페이지에 함께 표시됩니다. 법적 효력은 운영 약관을 따릅니다.
발행을 철회하면 공용 색인과 공유 페이지에서 내려갑니다. 다른 사용자의 목록에서는 사라지고, 이미 가져가거나 재발행한 사용자에게는 '철회됨'으로 표시됩니다. 가져간 사본은 그 사용자의 워크스페이스에 남습니다.

🧩 MCP 서버 (/mcp) 구현됨서버 전역

            
외부 AI 하네스(Claude Desktop · Claude Code · Gemini · Cursor 등)가 지식베이스를 읽는 표준 엔드포인트입니다. claire_api 프로세스 안에서 Streamable HTTP(stateless, JSON 응답)로 동작하며, 도구 10종은 모두 SQLite · FTS5 조회만 해서 LLM 쿼터를 쓰지 않습니다. 이 화면에서 구현됨은 현재 코드 그대로, 제안은 아직 없는 기능입니다.


            


            

              

                엔드포인트 · Discovery
                미인증 호출은 401 + WWW-Authenticate: Bearer … resource_metadata=…로 응답합니다. DNS 리바인딩 방어로 public_url 호스트와 localhost만 허용하므로 테마 전용 FQDN으로는 접속되지 않습니다.
              

              

                

                /.well-known/oauth-protected-resource · /.well-known/oauth-authorization-server
              

            


            

              

                테마 지정
                모든 도구가 theme 인자(번호 또는 레이블)를 받고, 생략하면 Theme 0을 읽습니다. REST와 달리 X-Claire-Theme 헤더와 테마 전용 FQDN은 MCP 도구에 적용되지 않습니다. 오른쪽은 상단에서 고른 테마를 읽는 호출 예시입니다.

🕸️ WebMCP — /syndication 페이지 도구 제안 · 미구현

            
WebMCP(W3C Web Machine Learning CG, Draft Community Group Report 2026-10-27)는 페이지가 document.modelContext.registerTool()로 도구를 등록하고, 브라우저 내장 · 확장 에이전트가 사용자가 열어 둔 탭 안에서 호출하는 방식입니다. 추가 토큰 없이 현재 세션으로 동작하고, 같은 출처(same-origin) 문서에만 보이며, 탭을 닫거나 등록 신호를 abort하면 사라집니다. 저장소에는 아직 관련 코드가 없습니다.


            


            

              

                WebMCP 도구 등록 (전역)
                끄면 /syndication이 도구를 등록하지 않고, 서버가 Permissions-Policy: tools=()를 보내 페이지 안의 다른 스크립트도 등록할 수 없게 합니다. 현재 Claire는 Permissions-Policy 헤더를 보내지 않습니다.
              

              
            


            

              

                이 테마에서 노출
                
              

              
            


            

              

                등록 방식
                사양이 정의하는 것은 명령형 registerTool()뿐입니다. 폼 속성(toolname · tooldescription · toolautosubmit)으로 + 구독 폼을 도구로 노출하는 선언형은 explainer 제안 단계라 실험 옵션으로만 둡니다.
              

              
            


            

              

                사용자 확인 정책
                사양에는 도구가 사용자 확인을 요청하는 API가 없습니다(README의 미해결 과제). 그래서 확인이 필요한 도구는 execute() 안에서 페이지 자체 확인 창을 띄워 응답을 기다리고, consequentialHint를 붙여 에이전트 쪽 확인도 유도합니다. 쓰기와 외부 발행은 정책과 관계없이 항상 확인합니다.
              

              
            


            

              

                에이전트 활동 표시
                toolactivated · toolcancel 이벤트를 받아 리더 하단 상태 표시줄에 🕸️ 에이전트: kb_ingest_item 실행 중처럼 표시하고 작업 기록에 남깁니다.

🪪 외부 IdP 로그인 제안 · 미구현서버 전역

            
지금은 운영자 한 명이 텔레그램 승인으로 로그인하고, 권한(owner · collaborator · readonly)은 토큰으로 나눕니다. 이 제안은 OpenID Connect IdP(Google · Microsoft Entra ID · Keycloak 등)로 여러 사용자가 로그인하고, 사용자마다 독립 워크스페이스(자기 테마 레지스트리와 SQLite DB 묶음)를 받게 합니다. 운영자의 텔레그램 로그인과 기존 데이터는 그대로 둡니다.


            

              

                로그인 방식
                운영자 계정은 IdP 클레임으로 만들거나 승격할 수 없습니다. 운영자는 계속 텔레그램 TELEGRAM_OWNER_CHAT_ID로만 인증합니다.
              

              
            

          


          

            
🔗 IdP 공급자

            
공급자마다 Authorization Code + PKCE(S256) + state · nonce로 로그인합니다. client secret은 브라우저에서 입력하지 않고 서버 비밀 파일이나 환경변수(CLAIRE_OIDC_<ID>_CLIENT_SECRET)로만 설정합니다.

            

              

                
사용공급자issuer · 방식client_id리디렉트 URI식별 키관리

                
              

            

            

              
              
              
              
            

            

          


          

            
🧾 계정 매핑 · 가입 정책

            

              

                사용자 식별자
                계정은 (iss, sub) 쌍으로만 식별합니다. 이메일은 바뀌거나 재할당될 수 있어 식별자로 쓰지 않습니다. GitHub는 OIDC가 아니므로 GET /user의 숫자 id를 sub로 씁니다.
              

              user_identities(iss, sub) UNIQUE
            

            

              

                가입 처리
                승인 후 생성은 첫 로그인 때 운영자 텔레그램으로 [승인] [거절] 푸시를 보냅니다. OAuth 승인 화면과 같은 방식입니다.
              

              
            

            

              

                허용 이메일 도메인
                쉼표로 구분합니다. 비우면 도메인 제한이 없습니다. Google Workspace는 hd 클레임도 함께 확인합니다.
              

              
            

            

              

                검증된 이메일 필수
                email_verified=true가 아니면 가입하지 않습니다. GitHub는 /user/emails의 verified를 씁니다.
              

              
            

            

              

                다른 IdP의 같은 이메일
                같은 이메일이라도 자동으로 합치지 않습니다. 기존 계정으로 로그인한 뒤 로그인 수단 연결에서 재인증해야 연결됩니다(계정 탈취 방지).
              

              수동 연결 고정
            

            

              

                세션 · 로그아웃
                세션은 기존과 같은 7일 슬라이딩입니다. IdP가 OIDC Back-Channel Logout을 지원하면 IdP에서 로그아웃하거나 계정이 비활성화될 때 Claire 세션과 이 사용자의 API · MCP 토큰을 함께 끊습니다.

🗄️ 사용자별 워크스페이스 · 데이터베이스 제안 · 미구현서버 전역

            
테마가 themes/{seq}/ 일련번호 디렉터리로 DB를 격리하는 방식을 한 단계 위로 올립니다. 사용자마다 users/{seq}/ 아래에 자기 themes.json과 테마별 claire.db · 볼트를 갖습니다. 기존 데이터는 그대로 운영자 워크스페이스(seq 0)가 되므로 이관이 필요 없습니다.

            

              
              
            

          


          

            

              
🧱 격리 구조

              
data/
├─ claire.db                     ← 운영자 워크스페이스 seq 0 · Theme 0 (현행 그대로)
├─ themes.json · themes/{n}/     ← 운영자 테마 (현행 그대로)
├─ auth/
│  ├─ api_tokens.json            ← 토큰마다 workspace_seq 추가
│  ├─ idp_providers.json         ← 공급자 메타데이터 (secret 제외)
│  └─ auth.db                    ← users · user_identities · user_sessions · invites
└─ users/{seq}/
   ├─ themes.json                ← 이 사용자의 테마 레지스트리
   ├─ claire.db                  ← 이 사용자의 Theme 0
   └─ themes/{n}/claire.db       ← 이 사용자의 추가 테마
vault/users/{seq}/…              ← 사용자 볼트

              
    
                
  • 경로는 인증 결과로만 결정: 세션 · API 토큰 · OAuth 토큰에 묶인 workspace_seq로 DB를 고르고, 요청 파라미터나 헤더로 다른 사용자 워크스페이스를 지정할 수 없습니다. 지정하면 존재를 숨기는 404를 돌려줍니다.
    • 
                
  • 테마는 워크스페이스 안에서만: ?theme=, X-Claire-Theme, MCP theme 인자는 자기 워크스페이스의 테마만 가리킵니다.
    • 
                
  • 운영자는 메타데이터만: 운영자 화면에는 용량 · 건수 · 상태만 보이고 사용자 문서 내용은 열 수 없습니다.
    • 
                
  • 백그라운드 작업 공정성: recover · refresh · expand 루프는 테마 대신 (워크스페이스, 테마) 쌍을 회전하며, 한 사용자의 대량 적재가 다른 사용자를 막지 않게 사용자당 상한을 둡니다.
    • 
                
  • 소각 규칙 재사용: 사용자 삭제는 테마 삭제 · 소각 프로토콜과 purged_tombstones를 워크스페이스 단위로 적용합니다.
