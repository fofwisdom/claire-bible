## 2. Locale Values and Resolution

**[code]** Two validators:

- Explicit selection (`PATCH /api/me`, `POST /api/locale`, `CLAIRE_LANG`): only `en` or `ko` after trim and lower case. `None` or `""` means automatic negotiation. Another value raises `InvalidLocale` (HTTP 400 `invalid_locale`; the `Settings` validator of `ui_lang` stops the start for `CLAIRE_LANG`).
- Passive negotiation (cookie, `Accept-Language`, Telegram `language_code`, POSIX variables): the primary subtag (`ko-KR`, `ko_KR.UTF-8` give `ko`). A value that is not supported is ignored, and the chain continues.

**[code]** Chains. The first step that gives a supported value wins.

| Surface | Chain | Where |
| :--- | :--- | :--- |
| Web request | `accounts.locale` (through `Principal.locale`) → cookie `claire_locale` → `Accept-Language` (RFC 9110 q-values, ties in header order, `q=0` excluded) → `CLAIRE_LANG` → `en` | `I18nMiddleware`, immediately inside the authentication middleware (`security.wrap_web_app`). On a public route the principal is anonymous, thus the cookie is the first step. |
| Telegram update | `accounts.locale` of the bot owner → Telegram `language_code` → `CLAIRE_LANG` → `en` | `resolve_update_locale()` (`src/claire/telegram/bot.py`) |
| Push notification | `accounts.locale` of the target account → `CLAIRE_LANG` → `en` | `push_locale()` (`src/claire/ops/notify.py`) |
| CLI | None. The CLI is English in ASD-STE100 (ID6). `resolve_cli_locale()` exists but no code calls it, and the CLI has no `--lang` option. | — |

The active locale lives in a `ContextVar`, thus each request, each Telegram update, and each `asyncio.to_thread` call has its own value. The middleware adds `Content-Language` only to `text/html` responses. JSON and protocol responses do not change with the locale.

## 3. Catalogs

**[code]** Each catalog is a flat JSON object: a dot-delimited key (`^[a-z0-9_]+(?:\.[a-z0-9_]+)+$`) to a string. `read_catalog_file()` rejects another shape. The two files have the same key set (2968 keys each at the basis commit) [measured].

- Placeholders: `{name}`. Python and JavaScript replace them with the same regular expression, not with `str.format`. A placeholder without a parameter stays as it is.
- Plural: `tn(base, count)` reads `<base>.one` when `count` is 1 and the key exists, else `<base>.other`.
- Lookup in Python: the locale catalog, then `en`, then the key itself. The browser catalog is already merged (`en` keys under the locale keys), and `ClaireI18n.t()` gives the key itself for a missing key.
- Main key domains: `console.*` (console, server-rendered), `console.js.*` (console scripts), `ws.*` (workspace), `synd.*` (`/syndication`), `bot.*`, `reader.*`, `auth.*`, `nav.*`, `home.*`, `context.*`, `list.*`, `share.*`, `directory.*` (public directory), `notify.*`, `stage.*`.

The test `tests/test_i18n_catalog.py` checks key parity and placeholder parity.

## 4. Delivery to Pages

**[code]** The server renders the text of each page for the active locale. A locale change needs a new GET of the page (`ClaireI18n.reload()`).

| Page | Mechanism |
| :--- | :--- |
| Templates of the account routes (login, setup, console shell, public directory) | `render_template()` (`src/claire/api/accounts_routes/common.py`): slots `$html_lang`, `$i18n_bootstrap_html`, `$locale_switch_html`, and `${t:key}` (escaped text). The syndication console partials also use `${th:key}` (a catalog value that is HTML, `console_syndication_panels.py`). |
| Workspace (`index.html`), `/syndication`, share page | `localize_page()` (`src/claire_bible/web/pages.py` calling `src/bible/web/pages.py`): slots `${html_lang}`, `${t:key}` (escaped text), `${tj:key}` (a JSON string for an inline script). One bundle is cached for each locale. |
| Public directory (`/accounts`, the root page of network mode) | Text from `t()` on the server. The entity tag includes the locale, and `Vary` includes `Accept-Language`. |

**[code]** Inline catalog: `<script id="claire-i18n-catalog" type="application/json">` before `i18n.js`, thus `ClaireI18n.t()` works before all network requests. `browser_catalog(scope)` selects the keys:

| Scope | Keys |
| :--- | :--- |
| `page` | All keys except the server-only domains (`auth.`, `bot.`, `cli.`, `notify.`, `directory.`) and `console.*` |
| `console` | `page` keys and `console.js.*` except `console.js.admin.*` |
| `console_admin` | `console` keys and `console.js.admin.*` (administrator area only) |
| `share` | `reader.*` and `share.*` only |

**[code]** `ClaireI18n` (`i18n.js`): `t()`, `tn()`, `applyDom()` (attributes `data-i18n`, `data-i18n-title`, `data-i18n-placeholder`, `data-i18n-aria-label`), `setLocale()` (`POST /api/locale`), `reload()`, `getLocale()`. The workspace scripts call it through `tr()` (`app.js`) and `rtr()` (`reader.js`).

**[code]** Language selection: `/settings/account` (`#pref-account-locale`: automatic, `en`, `ko`) sends `PATCH /api/me`. `/login` and `/setup` have no scripts, thus their switch is a form that posts to `POST /api/locale` ([`ACCOUNTS.md`](ACCOUNTS.md)).

## 6. Not Localized Now

**[code]** These texts do not come from the catalogs:

1. `src/bible/static/js/console_syndication.js`: the prototype data and the simulators of the syndication panels. ID5 gives them their keys when FP4 rebuilds the panels.
2. Text that an API response supplies: the progress messages of the ingestion cockpit, provider notes and the policy table of `/admin/providers`, error details.
3. Bot text that other modules make: the ingest report summary, the search result, `/status`, the pipeline progress steps, and the OAuth consent page ([`ACCOUNTS.md`](ACCOUNTS.md)).
4. The API reference page (`src/claire/api/templates/docs.html`) has a fixed `lang="ko"` and no catalog keys.
5. Two fixed Korean strings in scripts: a part of the placeholder of the re-ingest target field (`app.js`) and the label of the delete button of an identity provider row (`console_admin.js`).
6. The CLI progress lines of `heal_graph()` (`src/claire/store/db.py`), which `claire doctor --heal` and `claire audit --heal` print, are Korean. ID6 requires English.
7. The key `cli.preflight.header` is in the catalogs, but no code reads it.

## 7. Search Tokenizer (Content Language, Not Interface)

This section is here because the older i18n draft combined the two subjects. It is not a part of the interface language.

**[code]** `src/claire/retrieval/tokenizer.py`:

- `SearchTokenizer` (singleton from `get_search_tokenizer()`) uses `KoreanKiwiTokenizer` (kiwipiepy) for text that contains Hangul and `SimpleTokenizer` (regular expression `[0-9A-Za-z가-힣]+`) for other text. When kiwipiepy cannot load, it logs at level INFO and uses `SimpleTokenizer` for all text.
- `KoreanKiwiTokenizer` keeps morphemes with the tags `NNG`, `NNP`, `NR`, `NP`, `SL`, `SH`, `SN`, `XR`, `VV`, `VA`, and removes a list of frequent verb stems.
- User dictionary: `add_user_words()`. At start the tokenizer reads `data/user_dict.txt` or `data/dict/user_dict.txt` when the file exists.
- kiwipiepy is the optional dependency group `ko` (`pyproject.toml`). The container image installs it (`Dockerfile`, `--extra ko`).

**[code]** Use in `src/claire/store/db.py`:

- Index: the entity write adds the entity name and aliases to the user dictionary, then writes the observations, the aliases, and the extracted tokens into `entities_fts.body`.
- Query: `_fts_query()` runs the same tokenizer on the query and joins the quoted tokens with `OR`. Thus the index and the query use one tokenizer.
- Rebuild: `heal_graph()` rebuilds `entities_fts` with the tokenizer. `claire doctor --heal` and `claire audit --heal` call it ([`COMMANDS.md`](COMMANDS.md)).
