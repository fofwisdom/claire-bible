## 0. 작업 전에 알아 둘 것

1. **[코드] 모든 테마가 한 DB 파일을 쓴다.** v14부터 모든 테마의 데이터는 `data/claire.db` 하나에 있다. 테마 격리는 `kb_id` 컬럼으로만 이루어진다. 테마별 `Settings` 사본도 같은 `db_file`과 `data_dir`을 가리킨다(`KnowledgeBaseManager._settings_for_theme_info`). 따라서 다음은 **모든 테마가 공유한다.**
   - 파일 기반 상태: `data/jobs/*.json` 작업 기록, `providers.json`, `ingest_limits.json`, 텔레메트리
   - 이런 상태를 응답에 내보낼 때는 테마 권한으로 걸러야 한다. 예: `server.py`의 `_visible_active_jobs`(§4.3)
2. **[코드] 새 쿼리는 반드시 `kb_id`로 범위를 정한다.** `dbm.*` 함수 대부분이 `kb_id` 인자를 받는다. 이 인자를 빠뜨리면 기본값 0이 되거나 모든 테마를 대상으로 하게 된다.
   - 집행: `tests/test_kb_id_explicit.py`가 요청 경로 모듈(`api/`, `telegram_bot.py`, `ingest/`, `expand/`, `retrieval/`, `presentation/`, `graph_bundle.py`)에서 `store.db`·`store.queries`의 `kb_id` 함수를 이 인자 없이 부르는 곳을 찾아 실패시킨다. 모든 테마가 대상이면 `kb_id=None`처럼 명시해야 한다.
   - 이 검사 밖: 직접 쓴 SQL, `store.vectors`, `pipeline.ingest`
3. **[코드] 없는 테마는 다른 테마로 바뀌지 않는다.** `KnowledgeBaseManager.get_kb(ref)`는 찾지 못하거나 접근할 수 없는 테마에 `KnowledgeBaseNotFound`(`KeyError` 하위 클래스)를 던진다(§3). 참조를 생략한 경우(`None`, 빈 문자열) 주체 계정의 기본 테마(`theme.is_personal=True`, 관리자는 0)로 매칭한다. 레이블 부분 일치는 호출자가 `label_match="partial"`을 줄 때만 쓴다.
4. **[코드] 단일 테마 모드(`CLAIRE_MULTI_THEME=0`)에서도 Theme 0은 DB에서 읽는다(K8, Rev. 2.3).** 테마 정의·수정·삭제(`define_kb`·`update_kb`·`delete_kb`는 `RuntimeError`, HTTP `POST /kb`, `PATCH /`, `DELETE /`는 403)를 잠근다. `reset_kb`은 잠그지 않는다. Theme 0 메타데이터와 번호는 항상 DB의 `knowledge_bases` 테이블에서 읽어 일관된 코드 경로로 동작한다.
5. **[코드] 테마 소유권과 계정 귀속 (`account_id`)**: 모든 테마는 `KnowledgeBaseInfo.account_id`를 통해 특정 계정에 귀속된다(`claire.db` v15 `themes.account_id`). 관리자 테마는 `account_id = 1`이며, 멤버 계정이 생성한 테마는 해당 계정의 `account_id`를 갖는다.
6. **[코드] 기본 테마 불변식의 `theme.is_personal` 일원화 (Rev. 2.3)**: 멤버 계정(`account_id > 1`)의 기본 테마는 `id > 0, is_personal = 1`이다. 따라서 `tid == 0` 하드코딩을 제거하고 모든 기본 테마 불변식을 `theme.is_personal` 판정으로 일원화했다:
   - 기본 테마는 삭제할 수 없다 (`delete_kb`에서 `theme.is_personal`이면 `ValueError`).
   - The personal knowledge base takes writes only from its account (`kb_access.decide`, §4.1). The column `is_collaborator_accessible` is removed (claire.db version 28, unit CT-2).
   - 계정당 기본 테마는 정확히 1개이며, `claire.db`의 `idx_knowledge_bases_account_personal ON themes(account_id) WHERE is_personal = 1` 유니크 인덱스로 강제된다.
   - 테마 생략 시 `KnowledgeBaseManager.personal_kb_for(account_id)`로 해당 계정의 기본 테마를 단일 진실 공급원으로 조회한다.
7. **[코드] 테마 레이블 유일성 범위 `(account_id, label)`**: 테마 레이블 중복 검사는 전역이 아니라 **계정 범위** `(account_id, label)`로 판정한다. 서로 다른 계정 간에는 동일한 레이블명을 쓸 수 있으며, 동일 계정 내에서만 대소문자 무시 중복이 거부된다(`define_kb`, `update_kb`).

## 2. 저장 구조

**[코드] 레지스트리는 두 곳에 있다.**
- 정본은 DB의 `knowledge_bases` 테이블이다.
- `data/themes.json`은 `_save_registry()`가 원자적으로 다시 쓰는 사본이다.
- `reload()`는 DB 행을 읽고, JSON에만 있는 항목은 DB에 `INSERT OR IGNORE`로 넣는다. 그래서 두 곳이 다르면 DB 값이 이긴다.
- `define_kb`은 DB에 넣고 커밋한 뒤 JSON을 다시 쓴다. ID는 `seq`와 같은 일련번호(`_next_seq`)다.

**[코드] 기본 테마(`theme.is_personal=True`)는 항상 계정마다 1개 존재하며 삭제할 수 없다.** 관리자 계정의 기본 테마는 ID 0이며, 멤버 계정의 기본 테마는 `id > 0, is_personal = 1`이다. 모든 기본 테마는 협업자 접근이 꺼져 있다.

**[코드] 테마로 나뉘는 테이블**: `documents`, `entities`, `relations`, `embeddings`, `raw_inbox`, `extractions`, `proposals`, `jobs`, `refresh_queue`, `expand_queue`, `document_snapshots`, `document_presentations`, `doc_shares`, `purged_tombstones`, `syndication_dispatches`. `(kb_id, …)` 복합 인덱스는 `init_db`가 만든다.

**[코드] 레거시 DB 병합.** 멀티 테마 모드에서 `KnowledgeBaseManager(create_registry=True)`가 `reload()`할 때 동작은 다음과 같다.
- `data/themes/*/claire.db`가 있으면 `migrate_multi_db_to_single_db`를 부른다.
- 각 파일을 `ATTACH`하고, 행을 `INSERT OR IGNORE`로 `kb_id`를 붙여 복사한다.
- 다 끝나면 원본을 `claire.db.migrated`로 이름을 바꾼다.

## 3. 테마 조회 (`KnowledgeBaseManager.get_kb`)

**[코드]** 매칭 순서는 다음과 같다.
1. 비어 있으면(`None`, 빈 문자열) 관리자 계정의 기본 테마(`personal_kb_for(ADMIN_ACCOUNT_ID)`, 보통 테마 0). 관리 도구(CLI)의 기본값이다. HTTP 요청은 §4.1의 선택 규칙을 따른다.
2. 숫자 ID 정확 일치
3. 레이블 정확 일치(대소문자 무시)
4. 레이블 부분 일치(처음 걸린 테마): `label_match="partial"`일 때만

찾지 못했거나 접근할 수 없으면(`include_private=False`이면 비공개 테마) `KnowledgeBaseNotFound`를 던진다. 메시지는 같아서 비공개 테마의 존재가 드러나지 않는다. 다른 테마로 대신하는 분기는 없다(PRINCIPLES C1).

**[코드] 진입점별 처리**

| 진입점 | 레이블 일치 | 없는 테마 |

## 4. 요청이 테마에 도달하는 경로

### 4.1 HTTP (`server.py`)

**[코드]** 지식 베이스 선택 규칙(공유 지식 베이스 설계 §5.2, CT23, `_get_theme_ctx`):

1. **네임스페이스 라우트**: 경로만 선택한다. `/kb/{number}/…`는 그 공유 지식 베이스를 고정한다(`pinned_kb_id`, 네임스페이스 계정 없음, 모드와 무관). 고정이 없으면 네임스페이스 계정의 개인 지식 베이스(`personal_kb_for`)다. 개인 지식 베이스의 번호로 `/kb/{number}/…`를 요청하면 읽을 수 있을 때 그 계정 경로(`/@{u}/…`; 싱글 모드에서도 관리자의 `/@{username}/…`, 첫 설정 전에는 `/…`)로 308, 아니면 404다. 옛 링크 `/themes/{number}/…`·`/@{u}/themes/{number}/…`는 공유면 `/kb/{number}/…`로, 개인이면 그 계정 경로로 308이다(설계 §7).
2. **네임스페이스가 없는 라우트**(`any`·`system` 표면, 예: `/p/presentation`, `/api/me/data-bundles`, MCP 읽기 도구): 매개변수 `kb`(번호)가 필수다. 없으면 400 `kb_required`. `KnowledgeBaseManager.get_kb_by_reference`는 번호만 받는다(내부 ID·레이블·빈 값은 404).
3. **적재**(`/ingest`, `/ingest-stream`, 피드·타임라인 항목 적재): 자격증명 계정의 개인 지식 베이스에만 쓴다(`_get_personal_kb_ctx`). 다른 지식 베이스를 고정한 경로는 403 `kb_ingest_by_contribution`, 다른 계정의 네임스페이스는 404다.
4. **옛 이름**: 쿼리·본문 `theme`, `X-Claire-Theme` 헤더, 내부 ID 참조는 모르는 필드처럼 무시한다. `Deprecation`·`Sunset` 헤더도 없다. 문서를 다른 지식 베이스에서 찾아 대상을 바꾸는 폴백(`/share`, `/document`, 재생성, 프레젠테이션, 배급 원본)은 없다. 공유 토큰(`/p?s=`, `/p/presentation?s=`)은 토큰이 자기 지식 베이스를 정한다.
5. 개별 테마 FQDN 설정은 폐지되었다(O5). 기존 FQDN 접근은 `HostRouter`에서 308 정본 경로로 리다이렉트된다.

**[코드] 지식 베이스의 두 종류와 권한(CT-1, 설계 §6.2·§6.5·§11.2)**:

- **개인**(`is_personal=1`, `account_id`=계정, `knowledge_type` NULL): 계정마다 하나(CT1). 공개 또는 비공개. 소유자만 쓴다.
- **공유**(`is_personal=0`, `account_id` NULL, 항상 공개, `knowledge_type`은 `real`·`fictional`): 소유자가 없다. `define_kb(..., knowledge_type=..., account_id=창립자)`가 만들고 창립자는 `created_by_account_id`와 첫 `moderator` 멤버십이 된다(CT8). `POST /kb`는 `knowledge_type`이 없으면 400 `knowledge_type_required`다. 개수 한도는 없다(CT3, 등급의 `max_themes`는 쓰지 않는다). 레이블은 겹쳐도 된다.
- **권한 판정**은 함수 하나다: `claire.kb_access.decide`(§6.2 표 전체, §6.5, §6.6). 서버는 `_kb_decide`·`_require_kb`로만 쓴다. 익명은 404, 권한 없는 계정은 403 `kb_capability_required`다. 숨긴 문서는 공유 지식 베이스에서 `review` 권한자만, 개인 지식 베이스에서 그 계정만 본다.
- **Route capabilities and credential scopes (CT-2, design Sections 6.6 to 6.9)**:
  - Each entry of `api.security.ROUTE_POLICY` declares two values: the access level (the minimum scope of the credential) and the capability in the selected knowledge base. `_request_capability` reads the capability of the route; no handler selects it. `tests/test_credential_scopes.py` has the table of all routes that act on a knowledge base; a route that is not in the table fails the test.
  - Capabilities of a route: `none` (no knowledge base), `read`, `share` (make a share link), `write` (a write into the personal knowledge base of the account of the credential: ingest, re-ingest, publish, dispatch), and the capabilities of design Section 6.2 (`review`, `curate`, `maintain`, `settings`, `remove`, `delete`, and the others).
  - In a personal knowledge base, `read` and `share` stay, a decision about the knowledge base (`settings`, `delete`) needs `settings`, and each other capability is a write of the content. In a shared knowledge base a route with `write` gets 403 `kb_ingest_by_contribution` (CT4).
  - Scopes: `owner`, `write`, `readonly`. `write` replaces `collaborator`. In the personal knowledge base `write` reads, ingests, regenerates, and publishes. In a shared knowledge base `write` has only `read`, `contribute_direct`, `contribute_theme`, and `share`, also for a moderator or the admin. `readonly` has `read` and `share`.
  - A credential of an account whose scope is too small gets 403 `{"error": "scope_insufficient", "scope", "required"}` on a route that acts on a knowledge base. Under `/@{u}/` and on account, console, and admin routes the answer stays 404.
  - Regeneration (`/regenerate`, `/regenerate-stream`, `/document/regenerate`): minimum scope `write`, capability `maintain`. Thus a `write` token regenerates in the personal knowledge base, and a reviewer with the scope `owner` regenerates in a shared knowledge base (design Section 13.1 rule 5). `/synthesize` and `/research` write no document: capability `read`, minimum scope `owner`.
  - `share`: this capability is not in the table of design Section 6.2. Each account that reads a shared knowledge base has it (not a banned one); in a personal knowledge base only its account has it. In single mode a reader of the public knowledge base of the admin, an anonymous one included, has it (the rule from before this design).
  - Step-up (design Section 6.8): a route with `step_up=True` needs a session with a recent sign-in. A bearer credential gets 403 `step_up_requires_session`; an old session gets 401 `reauth_required`. Routes with it: `DELETE /kb/{number}/` and the admin moderator routes. `PATCH /kb/{number}/members/{account}` asks for it in the handler, only for a role change, because its other actions (approve, ban, remove) must be fast (Section 6.8 rule 2).
  - Syndication dispatch (`POST /api/syndication/dispatch`): the copy is an ingest, so its target is the personal knowledge base of the caller; a shared knowledge base as the target gets 403 `kb_ingest_by_contribution`. The source needs `read`. Federation publish and retract take only documents of the personal knowledge base of the caller.
- **프로바이더(§13.1 규칙 5)**: 공유 지식 베이스에서 사람이 시작한 작업(재생성, 프레젠테이션, 합성 등)은 **요청자 계정의 프로바이더 컨텍스트**로 실행한다(`IngestServicePool.get_service(..., acting_account_id=)`, `_provider_account_of`). 서버의 프로바이더를 쓰지 않는다. 재임베딩 필요 표시는 서버 임베딩과 비교한다(CT24).
- **워커(CT10)**: `_theme_services_for_cycle`은 공유 지식 베이스를 돌지 않는다(watch·refresh·expand·recover는 개인 지식 베이스만).
- **목록**: `list_account_kbs`는 계정이 소유한 것(개인), `list_selectable_kbs`는 선택기용(개인 + 모든 공유)이다.
- **콘솔·텔레그램**: `/settings/*`의 `?kb=`와 계정 백업·데이터 번들은 개인 지식 베이스만 받는다. 텔레그램의 테마 선택은 소유한 것만 보므로 공유 지식 베이스는 대상이 아니다(정리는 CT-8). 연합 발행(`POST /api/federation/publish`)도 개인 지식 베이스에서만 한다.

### 4.5 Collections: `GET /kb`, `GET /@{u}/kb`, `GET /themes` (CT-2, design Section 7)

The admin actions on moderators and the delete also write `admin_audit`. `GET /kb/{number}/moderation-log` (capability `people`) gives the log, the newest entry first.
- **[코드] Console**: for a moderator and the admin, `/moderation/kb/{number}` (`src/bible/static/js/console_kb.js`) has the tabs members and roles (with the join requests), settings, and moderation log. The knowledge type (Korean UI name "지식 유형") has its own dialog (`ClaireKbDialogs.openKnowledgeTypeDialog`, `PATCH /kb/{number}/` with only `knowledge_type`) on the settings tab and in the row menu of `/moderation/oversight`; a moderator or the admin corrects a wrong type with it (for example the type that a migration set for all knowledge bases). The save of the settings form does not send the type. `/moderation/oversight` (`src/bible/static/js/console_admin.js`) lists the shared knowledge bases without an active moderator and gives the role `moderator`. The active mutual collaborators of the founder become collaborators (`grant_mutual_collaborators`, Section 4.12).

### 4.8 Contributions to a shared knowledge base (CT-4, design Sections 9.1, 9.4 to 9.6)

- **[코드] Module**: `src/claire/contributions.py`. A contribution is a copy of a document of a personal knowledge base in a shared knowledge base K. The copy has its own document ID, its own files, and its own graph in K. `store/kb_collab.py` reads and writes `kb_contributions` and `kb_contribution_revisions`.
- **[코드] Direct contribution** (`contribute_direct`, one transaction): the checks are a duplicate in K (the same `canonical_url` or `content_hash`: 409 `contribution_duplicate` with the URL), a tombstone in K (409 `contribution_tombstoned`), and a completed extraction of the source (409 `document_not_extracted`). Then `copy_document` copies the `documents` row and the latest `extractions` row with a new ID (hidden, no watch, without the keys of `meta` that are results of the source knowledge base), and the contribution (origin `direct`, state `merging`, root = the source document) and its job are added. A contributor with the capability `review` needs no approval: `approved_at` is set at once. Else `approved_at` is NULL and the contributor can withdraw.
- **[코드] Merge job** (`run_merge_job`, `build_graph_from_extraction`): the job gives the copy its files (`copy_document_files`: local images, the text artifact, attachments; the uploaded source file of `raw_inbox` is not copied) from the document that the copy was made from (`copy_origin`: the root when the contribution has `revised_at`, else the source document; for a curation from a shared knowledge base the two are different), and builds the graph of K from the stored extraction (`ExtractionResult` JSON in `extractions.raw_response`). It makes **no LLM call** (CT24): no new extraction, no entity judge (`resolve_or_create(judge_fn=None)`: name, alias, and the automatic threshold only), and no relation judge. Embeddings use the provider of the server and the fixed embedding model of K; when the provider does not serve that model, the contribution gets `failed` with the code `embedding_model_unavailable`. For each copied image file, the image paths in the body of the copy (`detail`, `detail_html`) change from the source ID to the ID of the copy. The resolution log goes into the `meta` of the copy, so a purge can undo its decisions; the log is written also when the build fails part-way. A purge gives back the state of each entity before a merge of the copy, and removes from an entity that the copy created what the copy gave when another document merged into it later. A value that a document that stays also gave stays (`extract.decision.Provenance`: the resolution log and the extraction of each document). A relation that is there gets the copy as one more document in `sources` (`upsert_relation`), so it stays when one of its documents is purged. Success: `documents.hidden = 0`, state `visible`. Failure: state `failed` with a code in `decision_reason`; `retry_merge` adds a new job. The job is not one transaction (each entity and each relation is a commit). Thus the job changes the state at its end only when the contribution is still in the state and has the copy that the job started with (`kb_collab.finish_merge`); when a withdrawal or a removal came while the job ran, the job undoes the graph of the copy and ends with the error `contribution_changed`.
- **[코드] Jobs**: a merge job is a row of `jobs` with `source_type = 'contribution_merge'` and the payload `{"contribution", "revision"?}`. States: `pending`, `running`, `done`, `error`. `claim_job` takes a job for one process; a running job sets `jobs.updated_at` after each entity and each relation, and a job that is `running` with no progress for more than 15 minutes becomes `pending` again. The contribution routes run the jobs of K in the request. Each service job of `IngestService` runs the jobs that wait when it ends (`run_waiting_merge_jobs`), with the settings of the server, so the worker loops also run them.
- **[코드] Withdrawal and review** (`withdraw`, `approve`, `reject`, `set_hidden`, `set_updates_frozen`, `remove`): the contributor withdraws while `approved_at IS NULL` (the copy, the copies of its revisions that wait, and the row are deleted, no tombstone); after the approval 409 `contribution_approved`. The withdrawal of a contribution with the origin `auto` sets the flag "never contribute" of the source document (`withdraw` returns `contribution_blocked`), so the rule does not send it again. The purge of a copy (`_purge_copy`) cleans the graph of the copy itself and calls `purge_document_cascade` with `heal=False, vacuum=False`: a review action runs no graph heal and no `VACUUM`. An approval is final; for a pending contribution it starts the merge job. A reject is for a pending contribution and needs a reason code. Hide and unhide change `documents.hidden` and the state; `POST /document/hide` on a copy does the same. Remove needs a reason code, purges the copy with a tombstone, and sets the state `removed`. Reason codes: `off_subject`, `wrong_knowledge_type`, `duplicate`, `low_quality`, `spam`, `other`. Each review action writes `kb_moderation_log`. A purge of a copy from another entry point (`POST /document/purge` in K) sets its contribution to `removed` (`purge_document_cascade`).
- **[코드] Revisions** (`start_revisions`, design Section 9.5): `ingest.pipeline.extract_resolve_store` calls `_start_contribution_revisions` after each successful extraction. When the document is the root of contributions and the `content_hash` of a copy differs from the root (`documents.content_hash` is the hash of the fetched text; regenerate does not change it), the new version and its extraction are copied into K without graph. For a visible or hidden contribution the merge job builds the graph of the new copy, points the contribution to it, purges the old copy, and records a row in `kb_contribution_revisions`; there is no approval, and the state stays. For a contribution in `merging` the revision waits until the first merge is complete (the job goes back to `pending`). When the first merge fails, the new version replaces the failed copy (`kb_collab.replace_failed_copy`; the state `failed` and its code stay), so a retry merges the newest version. For a pending or failed contribution the new version replaces the copy. The newest version wins: when a new revision starts, each older revision that still waits is closed (`failed`) and its copy is purged. The job points the contribution to the new copy only when the revision and the contribution are still as the job found them (`kb_collab.apply_revision`). A contribution with stopped updates (`updates_frozen`) and a closed one keep their version. The revisions do not read the visibility of the personal knowledge base (CT26). When the root is deleted, the copies stay.
- **[코드] Contribution to a theme** (`submit_to_themes`, CT-6, design Sections 9.2 and 9.3): a submission (`kb_submissions`) has one item (`kb_submission_items`) for each document. The theme of an item is the theme that the account selected (`routed_by = 'account'`) or the theme match of the document (`match_document`, `routed_by = 'server'`, with the score). An item with no theme has no target. The targets are the active shared knowledge bases of the theme where the account is not banned. In each target: a reviewer (a collaborator, a moderator, or the admin) contributes with the approval and the merge job runs after the commit; each other account makes a contribution in the state `pending` with a hidden copy, no graph, and no merge job. A duplicate, a tombstone, a document with no extraction, and the pending limit skip the target; the item keeps the reason. Each contribution has `origin = 'bulk'` and `submission_item_id`. The decision in one knowledge base does not change the contribution in another one.
- **[코드] Limits**: `read_limits` gives the `server_settings` key `submission_max_documents` (20); `write_limit` sets it (an integer of 1 or more) through `PUT /api/admin/themes/settings`. The limit of the pending contributions of one account in one knowledge base comes from the reputation (`reputation.pending_limit`, Section 4.10).
- **[코드] Review help and agreement**: `decision_of` gives the decision of a knowledge base on a contribution; the contribution list gives a reviewer the decisions of the other knowledge bases on the same item, the theme score, and the score of the document against the signature of the knowledge base. `decision_agreement` gives, for each shared knowledge base, the part of its decisions that agree with the majority of the other knowledge bases, for items with 3 or more decisions; `GET /api/admin/themes` shows it. An approval is a decision only when another account made it (`kb_collab.approved_by_another`: `approve` sets `decided_at`; the approval that a contribution of a reviewer gets when it is made does not). The approval rate of the reputation uses the same rule, so the approval of a reviewer that was purged later (`approved_by_account_id` NULL) still counts. The server makes no decision from it.
- **[코드] Curation** (`curation_source`, `curate`, CT-7, design Section 9.7): the source S is another knowledge base that is a member of one active theme of K (`themes_store.share_a_theme`); a private personal S is "not found". A document of S must be not hidden; in a shared S its contribution must be `visible`. The copy is a contribution with `origin = 'curation'`, `curator_account_id` and `approved_by_account_id` = the reviewer, `source_kb_id` = S. The credit and the root: for a shared S, `contributor_account_id`, `root_kb_id`, and `root_document_id` of the contribution in S; for a personal S, the owner of S and the document itself. Thus the copy follows the revisions of the root (Section 4.8). The checks, the hidden copy, and the merge job are the ones of a direct contribution (`_add_copy`). The moderation log gets `curate`.
- **[코드] Curation across servers** (federation design Section 11, unit KF3): the source can be a shared knowledge base of another server that is in a theme of K (`remote_source` of `POST /kb/{number}/curations`, `GET /kb/{number}/remote-sources`). The sidecar reads the document with its extraction; `curate_remote` makes the copy with the checks of `check_new_source` and a contribution with the origin `curation`, no local source and root, and the remote source, root, and credit in the columns `remote_*`. The merge job is the same (no file copy: the copy has no source files). An `Update` of the origin starts a revision without approval (`start_remote_revisions`, the rules of the revisions above); a `Delete` of the origin hides the copy and puts it in the review queue (`origin_removed`; `set_hidden` with unhide is the decision "show again"). A fork keeps the remote columns of a copy. Details: [`KNOWLEDGE_FEDERATION.md`](KNOWLEDGE_FEDERATION.md) Section 12.4.
- **[코드] Contributions across servers** (federation design Sections 12.1 and 12.2, unit KF4): `submit_to_themes` gets the canonical `origin` of the server (None: no offer goes out). While the switch `federation` is on, each shared knowledge base of another server that is a member of the theme of an item is a target too: `knowledge_federation.offers.send` puts an `Offer` of the account actor in the outbox, or records the target as skipped with the reason. `remote_kb_id` is the direct choice of one such knowledge base; it needs a grant of the role collaborator (403 `grant_required`) and gives items without a theme. The submission views show these targets with the decision of the other server. On the receiving server an `Offer` makes a contribution with no contributor account, the remote credit and root (`contribute_remote`, origin `bulk` and state `pending` with a hidden copy, or origin `direct` and state `merging` with a grant in effect and a reputation that is not `low`); the review queue orders it by the reputation that this server computes from its own decisions (`reputation.compute_remote`), and the decision of a reviewer goes back as `Accept` or `Reject`. Limits `remote_account_pending_limit`, `remote_domain_pending_limit`, `remote_domain_daily_offers` (`contributions.LIMITS`, `PUT /api/admin/themes/settings`). A contributor of another server cannot withdraw a pending contribution. Details: [`KNOWLEDGE_FEDERATION.md`](KNOWLEDGE_FEDERATION.md) Section 13.
- **[코드] Fork** (`fork_copy`, CT-7, design Section 9.8): the route makes the new shared knowledge base with `define_kb` (label `<label> (fork)`, the knowledge type and the seed entities of the source; the requester is the founder and the moderator), then `fork_copy` runs in the request: first all rows in one transaction, then, after the commit, the files of each copy (one short transaction for each document). When a file copy fails, `fork_copy` deletes the files that it copied and raises. It copies each document that is not hidden and has a `visible` contribution (with its latest extraction and its files), each entity and relation that has a copied document in `sources` (new IDs; `sources` holds the copies), the embeddings and the FTS rows of the copied entities, and the `resolution_log` of each document with the new entity IDs. It makes no LLM call and no embedding. Each copy gets a contribution with `origin = 'fork'`, `state = 'visible'`, the credit and the root of the source contribution, `curator_account_id` = the requester, and `approved_at` = the fork time. The fork gets `embed_provider`, `embed_model`, `forked_from_kb_id`, `forked_at`, and a membership (`source = 'fork'`) in each active theme of the source. When the copy fails, the route deletes the new knowledge base. A copied entity keeps only the observations and the aliases that the copied documents gave (their resolution logs and their extractions), so a hidden document of the source gives nothing to the fork; the FTS row of a changed entity gets a new body. The name, the type, and the embedding are those of the source entity. Cost: one read of the log and the extraction of each copied document, and a new FTS body for each changed entity, in the transaction of the rows.
- **[코드] Console**: `/moderation/kb/{number}` (`console_kb.js`) has the tabs review queue, contributions, and curation for a reviewer. `/settings/kb` has the tab of the submissions of the account.

### 4.9 Themes: subject judgement and document match (CT-5, design Sections 8.2 to 8.5)

- **[코드] Module**: `src/claire/theme_judgement.py`. It makes no LLM call. `store/themes.py` reads and writes `themes`, `theme_knowledge_bases`, `theme_remote_knowledge_bases`, `kb_signatures`, `kb_judged_counts`, and `kb_document_matches`.
- **[코드] Signature** (`compute_signature`): the 256 entities of a public knowledge base with the most visible source documents; keys `(type, norm_name)` of the entities and of their aliases; the centroid of their embeddings when they have one model. Fewer than 5 counted documents: no signature. The fiction-like documents of a personal knowledge base do not count.
- **[코드] Similarity and clustering** (`similarity`, `cluster`): weighted Jaccard of the tf-idf vectors, plus `0.3 ×` the cosine of the centroids when the two knowledge bases have one embedding model; average-linkage clustering of the shared knowledge bases of one type until the next merge is below `theme_match_threshold`.
- **[코드] Run** (`run_judgement`): signatures; clusters; stable identity (a cluster takes the theme whose computed members overlap with a Jaccard of 0.5 or more; a cluster with no such theme takes the target of a merge that has half or more of the cluster as pinned members; else a new number); memberships (a pinned or excluded row stays; a knowledge base without a signature keeps its rows; a knowledge base that the admin excluded from its cluster theme gets a theme of its own and keeps that theme in later runs); public personal knowledge bases attach to each `real` theme with an average score at or above the threshold and never make a theme; state `empty` for a theme with no shared knowledge base, local or remote (the rows of personal knowledge bases stay); label ("A · B") and description from the two and the ten entities with the highest summed weight, unless the label is locked; the theme signature; `last_activity_at`; the document matches of personal knowledge bases.
- **[코드] Document match** (`DocumentMatcher`, `match_document`): the keys of a document are the keys of its source entities; the score with a theme is the idf-weighted part of those keys in the theme signature; the match is the theme with the highest score at or above `document_match_threshold` when the document has 3 keys or more (a tie goes to the theme with more shared knowledge bases). `seed_score` gives the score with seed entities. The ingest pipeline computes the match of a document of a personal knowledge base after its extraction (`_match_document_theme`).
- **[코드] Transactions of a run**: the run commits its changes; the caller does not have to commit. The read part (`_plan`) computes the signatures, the clusters, and the attachments and writes nothing. Then one transaction stores the signatures and the counts of `kb_judged_counts` and changes the themes and their members. Then one transaction for each personal knowledge base stores its document matches. The last transaction stores the time of the run; a run that stops before it is due again.
- **[코드] Schedule**: `run_is_due` is true once a day and when a public knowledge base has 20 new visible documents since the last run. Each run stores the count of all visible documents of each public knowledge base in `kb_judged_counts` (also for a knowledge base without a signature; the fiction-like documents count). A knowledge base with no stored count was in no run: all its visible documents are new. The migration step `_migrate_judged_counts` of `store/db.py` makes the table at each start, with no new schema version. Each service job of `IngestService` calls `run_theme_judgement_if_due` when it ends; the admin starts a run with `POST /api/admin/themes/judge`.
- **[코드] Adjustments** (design Section 8.3, admin routes in [`API_HTTP_CONTRACT.md`](API_HTTP_CONTRACT.md)): rename (locks the label), pin, exclude, merge (`merge_themes`: the page of the merged theme gives 308; the shared members, local and remote, are pinned to the target; an attached personal knowledge base gets no pin and attaches again by the next run), and split (make a theme, then pin). Each one stays after a new run.
- **[코드] Remote knowledge bases** (federation design Section 8.2, unit KF2): step 4b of `run_judgement` attaches each shared knowledge base of another server (a record of `knowledge_federation.remote_kbs` with a signature) to the local theme of its type with the highest average score with the local shared members, when the score is at least `theme_match_threshold`. It never makes a theme and does not change the clusters, the label, or the signature of a theme. The rows are in `theme_remote_knowledge_bases`; pin, exclude, and merge apply to them (`PUT /api/admin/themes/{number}/remote-knowledge-bases/{remote_id}`). `run_is_due` is also true after a new or changed record. Details: [`KNOWLEDGE_FEDERATION.md`](KNOWLEDGE_FEDERATION.md) Section 11.5.
- **[코드] Pages**: `/themes/{number}/` gives the theme as JSON or HTML (the namespace middleware sends a theme number to it; a number of a knowledge base still gets the 308 of the old links). The view lists the shared knowledge bases of this server, then those of other servers (`remote` true, with `server` and the origin link `url`), then the personal ones; it has the counts `shared_knowledge_bases` and `remote_knowledge_bases`. The root page of network mode shows the themes first, then the federated servers and the recent activity across servers (`GET /explore/federation`).
- **[코드] Changes of the method of the design, not calibrated (CT25)**: `idf = ln(1 + N / df)` in place of `ln(N / df)` (the design formula gives 0 for a key of each signature, so two knowledge bases of one type never match), and tf-idf vectors with the sum 1 (else the sizes of the knowledge bases decide the similarity). The defaults `theme_match_threshold = 0.25`, `document_match_threshold = 0.5`, and `seed_match_threshold = 0.5` have no calibration: the development data has only one knowledge base with documents. With real embeddings the cosine of unrelated centroids is not near 0, so the threshold needs data from a server with some shared knowledge bases.
- **[코드] WebUI**: the theme page (`renderThemeDetail` in `public_kb.js`) has the actions "Contribute to this theme" and "Make a shared knowledge base of this type" for a signed-in account, and a fork action for each shared knowledge base of this server in the list. The home overview has the theme card (`#home-themes`, `renderHomeThemes` in `app.js`): the links to at most 8 themes.

### 4.10 Reputation and campaign message (CT-11, design Sections 8.6 and 8.7)

- **[코드] Module**: `src/claire/reputation.py`. `compute` gives the reputation of an account from the data at each use, so a decision takes effect at once; `refresh` also stores it in `account_reputation` (for the lists, and for the day of the standing message).
- **[코드] Fiction share**: the fiction-like documents (`kb_document_matches` with a `fictional` theme) divided by the visible documents of the personal knowledge base. A fiction-like document does not count when the account has a contribution with that root in a shared knowledge base of the type `fictional` that is visible or approved (`kb_collab.roots_in_fictional_kbs`).
- **[코드] Approval rate** (`kb_collab.decisions_of_account`, `approval_rate`): the window is `reputation_window_days` (180). Only the contributions that the account made itself count (origins `direct`, `bulk`, `auto`), and only a decision of another account: an approval by the contributor itself (a reviewer of K) is not a decision. A rejection or a removal counts only with the reason codes `off_subject`, `wrong_knowledge_type`, `low_quality`, `spam`. A knowledge base with more than one third of the decisions keeps its own rate and gets the weight of one third. No value with fewer than `reputation_min_decisions` (10) decisions.
- **[코드] Level** (`level_of`): `low` with a fiction share of at least 0.5 or a rate below 0.2; `limited` with a share of at least 0.2 or a rate below 0.5; else `good`. The numbers are `server_settings` keys (`reputation.SETTINGS`); `PUT /api/admin/reputations/settings` writes them. They are not calibrated: the development data has no decisions.
- **[코드] Effects**:
  - Theme attachment: the judgement does not attach a public personal knowledge base of the level `low` (`run_judgement` step 4). The theme view does not list it; `limited` is listed after the others with `"limited": true`. `curation_source` refuses a personal source of the level `low` with `source_not_in_theme`.
  - Direct contribution (`contributions.direct_mode`): with `low` the contribution is `pending` (hidden copy, no merge job), also for a collaborator or a moderator; the pending limit of the level applies (409 `pending_limit`). The admin has no reputation rule.
  - Contribution to a theme (`submit_to_themes`): a reviewer of the level `low` gets a pending contribution; the pending limit is `pending_limit_good` (100), `pending_limit_limited` (20), or `pending_limit_low` (5).
  - Review queue: `GET /kb/{number}/contributions?state=pending` for a reviewer is in the order `good`, `limited`, `low`, then the oldest first. A reviewer sees `contributor_reputation` (`level`, `approval_rate`).
  - Automatic contribution: `reputation.auto_contribution_limit` (no limit, `auto_contribution_limited_documents`, or 0 for paused) limits a run (Section 4.12).
- **[코드] Campaign notices** (`src/claire/campaign.py`): after the theme match of a new document of a personal knowledge base, `IngestReport.notices` gets `fiction_like_document` (with `document`, `theme`, `theme_label`) when the match is a `fictional` theme, and `fiction_standing_message` with the first ingest of each UTC day of the account (`account_reputation.campaign_day`). Each notice has `message` (English). The HTTP result of an ingest has them in the report; the Telegram reply shows them in the locale of the chat (catalog keys `campaign.*`); the CLI command `ingest` prints them as `NOTICE:` lines.
- **[코드] Notices in each entry point**: the ingest forms of the WebUI show the standing message each time (`#ingest-fiction-notice` in `src/bible/templates/partials/common_ingest_modals.html`), and the result of an ingest shows a `fiction_like_document` notice with the action "Contribute to this theme" (`ingest_dialogs.js`). The Telegram reply has a button for the same action (`contribute_callback_data`, callback prefix `ctb:`). The CLI prints the line `ACTION: Contribute to this theme: claire contribute submit <document> --theme <number>`. The tab reputation of `/settings/kb` shows the level, the signals, the limits, and the fiction-like documents (`GET /api/reputation`). MCP has no ingest tool, so it shows no notice.

### 4.11 Effects on other subsystems (CT-8, design Section 13)

- **[코드] Ingest**: an ingest pinned to a shared knowledge base gets 403 `kb_ingest_by_contribution` (`_require_kb`; each route with the capability `write`).
- **[코드] Workers**: `watch_due_documents`, `pending_refresh`, and `pending_expand` take no row of a shared knowledge base (`_NOT_SHARED_KB` in `store/db.py`), also when the caller gives the ID of a shared knowledge base. A copy has `watch_enabled = 0` from the start.
- **[코드] Account purge** (`AccountStore.purge`, `kb_collab.purge_account`): the memberships, the automatic rule, the contribution blocks, the mutual collaborations, the stored reputation, and the theme rows of the personal knowledge base are deleted. A pending contribution of the account is deleted with its hidden copy. Each other contribution stays with `contributor_account_id = NULL`; the account goes also from `curator_account_id`, `approved_by_account_id`, `kb_memberships.decided_by_account_id`, `knowledge_bases.created_by_account_id`, and `kb_moderation_log.actor_account_id`. An account cannot ask for its own deletion: only the admin schedules a deletion and purges, so `/settings/account` has no control for the option. With `delete_activity_records` (the body field of the admin purge action) the submissions with their items are deleted and the reason texts of the account in the moderation log are cleared; no document, graph, or contribution changes.
- **[코드] Account backup**: a backup has the knowledge bases with `account_id` = the account, which is the personal one. The restore (`_is_personal_target`) replaces only the personal knowledge base of the account. A knowledge base of the archive that is a shared knowledge base now (a backup made before version 28) is skipped; the result lists it in `skipped_knowledge_bases`.
- **[코드] Federation**: the publish route has the capability `write`, so only the personal knowledge base publishes. The removal of a contribution purges the copy with `purge_document_cascade`, which adds the `Delete` tasks for a published object.
- **[코드] Telegram**: the command `/kb` (before: `/theme`) selects the personal knowledge base or a shared knowledge base (`AccountThemeScope.readable_kbs`, `get_readable_kb`). `/search` uses the selection. Ingest, `/failed`, and `/retry` use the personal knowledge base when the selection is a shared one (`resolve_selected_theme`). The ingest reply shows the campaign notices (Section 4.10).
- **[코드] CLI**: `claire theme` (list, judge, rename, unlock, pin, exclude, free, merge); see `COMMANDS.md`.
- **[코드] Data bundle** (design Section 13.2): `POST /kb/{number}/graph/bundle` (capability `settings`: a moderator or the admin) makes the data bundle of a shared knowledge base: the visible documents, their graph, and the contributions with the public number of the account with the credit; no pending or hidden copy. The control is the card "Data bundle" on the settings tab of `/moderation/kb/{number}`. Details: [`GRAPH_BUNDLE_REVIEW.md`](GRAPH_BUNDLE_REVIEW.md) Section 6.3.

### 4.12 Automatic contribution and mutual collaboration (CT-13, design Sections 9.9 and 9.10)

- **[코드] Module**: `src/claire/auto_contribution.py`. The store functions are in `store/kb_collab.py` (`kb_auto_rules`, `kb_auto_rule_themes`, `kb_contribution_blocks`, `kb_mutual_collaborations`).
- **[코드] Server switch**: the `server_settings` key `kb_auto_contribution` (`on` or `off`; no row is `off`). While it is off, `run_account` and `run_all` do nothing and each rule keeps its settings. Settings: `auto_match_threshold` (0.5, not calibrated) and `auto_run_documents` (50).
- **[코드] Rule**: one row for each account: state `active` or `paused`, `to_memberships`, `to_mutual`, `include_uploads`, and the themes of the rule. `targets` gives the active shared knowledge bases: the ones where the account is an active member, the ones that an active mutual collaborator founded (`created_by_account_id`), and the members of the themes of the rule (a merged theme is replaced by the theme that it was merged into). A knowledge base where the account is banned is no target.
- **[코드] Candidates** (`candidates`): the score of a document for a target K is the document match with the signature of K, else with the signature of a theme of K, else with the seed entities of K (`DocumentMatcher.score`, `seed_score`); a K with none of them has no candidate. Not candidates: a hidden document, a document with the flag "never contribute" (`kb_contribution_blocks`), a pasted text (`source_type = 'text'`), a document with no URL (an uploaded file) unless the rule has `include_uploads`, a document with no extraction, a document with a contribution of the account in K in any state, and a document with a duplicate or a tombstone in K. The keys of all documents of the personal knowledge base are read one time for each run (`personal_document_keys`) and used for each target; the checks that read the database for one document run only for a document at or over the threshold. A document whose automatic contribution the account withdrew has the flag "never contribute" (Section 4.8).
- **[코드] Run** (`plan`, `run_account`, `run_all`): the mode of a target is `approved` for a collaborator or a moderator, `direct` for a member, `pending` for each other account; the origin is `auto`. Limits: `auto_run_documents` for each run and target; the reputation `limited` gives `auto_contribution_limited_documents`, `low` pauses the rule; a `pending` target also has the pending limit of the level. `plan` writes nothing: it is the dry run. Each contribution is its own transaction.
- **[코드] When a run starts**: after the extraction of a new document of a personal knowledge base (`ingest.pipeline._auto_contribute_document`, for that document only); when the rule is saved (`PUT /api/auto-rule`); when a mutual collaboration starts (the two accounts); when a shared knowledge base is made, forked, or gets new seed entities; after each judgement run (`run_theme_judgement_if_due`, `POST /api/admin/themes/judge`); when the admin turns the switch on. The merge jobs run after the run.
- **[코드] Mutual collaboration**: `request_mutual`, `accept_mutual`, `end_mutual`. When an account founds a shared knowledge base (`POST /kb`, fork), `grant_mutual_collaborators` gives each active mutual collaborator the role `collaborator` at once (`decided_by_account_id` = the founder, log action `grant_collaborator` with the reason `mutual_collaboration`). The end does not change a role. An account that is not `active` does not count (a suspension is a pause); a purge deletes the rows.
- **[코드] MCP**: the tools `kb_candidates` (read: the candidates for a knowledge base, a theme with its shared knowledge bases of other servers, or one shared knowledge base of another server (`remote_knowledge_base`), with scores) and `kb_submit` (scopes `owner` and `write`: the same as `POST /submissions`).
- **[코드] Targets on other servers** (unit KF5, federation design Section 12.3): `remote_targets` gives the records of remote knowledge bases that the rule selects: with `to_memberships`, the ones that gave the account a grant in its term (`grants.kb_iris_in_effect`); the remote members (not excluded) of the themes of the rule. `to_mutual` selects no remote target. `remote_candidates` scores with the signature of the record (else the signature of a local theme with the record); the other exclusions are those of `candidates`, and a document with a row of `kf_outbound_offers` for that knowledge base does not go again (`offers.automatic_offered`; a row that was skipped or rejected for a reason that can change, `offers.RETRY_REASONS`, does not count). The duplicate and tombstone checks are on the other server. The mode is `approved` with a grant in its term (the other server decides at the end), `pending` without one, and `closed` when the record says that the server accepts no automatic contributions (`remote_kbs.accepts_automatic` is False; no offer). A run sends one `Offer` with `claire:automatic` for each candidate (`offers.send` with no submission item), with the same limits. `plan`, `run_account`, and `run_all` need `origin`, the canonical origin of this server (`contributions.canonical_origin`), or None: then no remote target. `remote_state` tells why a rule has no remote target. Details: [`KNOWLEDGE_FEDERATION.md`](KNOWLEDGE_FEDERATION.md) Section 15.
- **[코드] CLI**: `claire contribute rule show` and `claire contribute rule set` (with the dry run; `--apply` saves the rule) for the admin account.

## 6. 알려진 한계와 미검증

- **[코드] 레거시 병합 실패를 삼킨다.** `reload()`는 `migrate_multi_db_to_single_db`의 예외를 `log.warning`으로만 남기고 계속한다. 그러면 `claire migrate`가 성공으로 끝나고 서비스도 시작되지만, 옛 테마 데이터 일부가 빠진 상태가 된다(PRINCIPLES C2·E3 위반).
  - 단순히 예외를 다시 던지게 고치면 재시도가 안전하지 않다. 병합은 DB 파일 단위로 커밋하고, 자동 증가 키 테이블은 `id`를 빼고 복사한다. 그래서 부분 실패 뒤에 다시 실행하면 그 테이블의 행이 중복될 수 있다.
- **[코드] 삭제(`purge=False`) 뒤에 남은 데이터 행에는 접근할 수 없다.** 해당 `kb_id`의 행이 DB에 남지만 어느 테마에서도 보이지 않는다. 정리하는 명령은 확인하지 못했다.
- **[미검증]** `import-graph --theme`은 테마의 `db_path`(현재는 단일 DB)를 대상으로 한다. 가져온 행에 `kb_id`가 붙는지는 확인하지 않았다.
- **[미검증]** 텔레그램 `/kb`와 MCP 도구의 테마 지정에서 비공개 테마 접근이 어떻게 검사되는지는 이 문서 작성 시 확인하지 않았다.
