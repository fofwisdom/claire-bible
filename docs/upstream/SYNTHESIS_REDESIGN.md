# 종합(Synthesis) 재설계 — 다중 노드 → 조사 병행 → 문서 생성 → 재흡수

작성일: 2026-06-24 · 상태: **설계 초안(미구현) — advisor 검토 반영본** · 기준: [GOALS.md](../GOALS.md) 트랙3(UX) 확장

> ⚠️ 초안 작성 후 아키텍트 검토에서 세 가지 치명적 사실이 드러나 본문을 정정했다(§9 참조):
> ① 모든 Gemini 호출은 프로세스 전역 락+throttle로 **직렬화**된다 → "병렬 조사"는 무효 가정.
> ② **dedup(MinHash 0.90)이 synthesis 문서에 적대적** → 별도 취급 필수.
> ③ 순환방지는 `onehop:` 게이트가 아니라 `expand_max=0`이 이미 담당.

> 큰 기능이라 구현 전 계획을 먼저 남긴다(사용자 지시). 구현 착수 시 이 문서를 갱신하며 진행.

---

## 1. 비전 (사용자 의도)

> "의도가 흥미로운 노드를 여럿 섞어서, **수집 내용 + 그 관계성 + 각 노드 컨텍스트에 맞는 추가 웹조사**를 병행해서, **가장 적절한 문서를 생성**해내는 용도. 괜찮은 문서가 나오면 **그걸 다시 claire에 흡수**시킨다."

종합은 단순 "선택 노드 요약"이 아니라, **여러 관심 노드를 출발점으로 새로운 종합 지식을 합성하고 그 결과를 다시 지식베이스로 환류(feedback loop)** 하는 기능이다. 개인 지식베이스의 핵심 가치인 "기존에 쌓아둔 것과의 연결"을 **생산(generative)** 방향으로 확장한다.

## 2. 현재 구현과 한계

### 현재 동작 (코드 근거)
- UI: `synthSet`(Set) — `Ctrl/Cmd+클릭` 또는 노드 상세의 `➕ 종합에 추가`로 노드 수집, 칩으로 표시, `🧩 종합 (N)` 버튼. (`graphview.py` `toggleSynth`/`addToSynth`/`renderChips`)
- 요청: `synth()` → `POST /synthesize {node_ids, query}` (`server.py` `synthesize_route`)
- 서버: `graphview.synthesize(conn, provider, entity_ids, query)`
  - `synthesis_context()` — 선택 노드의 **관찰·연결(이웃 관계 나열)·출처요약**을 결정론적 텍스트로 조립
  - `provider.summarize_search(q, context)` — **검색 정리와 동일한 LLM 경로** 재사용
  - 반환: `{answer, entities, query}` — 텍스트만, 화면에 표시하고 끝

### 한계 (재설계 동기)
1. **웹조사 없음.** 종합은 그래프 내부에 이미 적재된 지식(관찰·출처요약)만 본다. "각 노드 컨텍스트에 맞는 추가 웹조사"가 빠져 있다 → 새 정보 유입이 0.
2. **관계성 분석이 얕다.** `synthesis_context`는 이웃 관계를 단순 나열(`type → 이름`)할 뿐, 선택 노드들 **사이의** 관계 구조(공통 이웃, 연결 경로, 대비점)를 분석하지 않는다.
3. **결과를 흡수하지 않는다.** 생성된 종합 문서는 화면 표시뿐 — 다시 claire에 적재되지 않아 일회성이다. 좋은 종합이 지식베이스를 키우지 못한다.
4. **노드 선별 UX가 번거롭다.** `Ctrl+클릭`은 발견적이지 않고, 모바일에선 어렵다. 검색 결과·경로·문서에서 모은 노드를 종합으로 넘기는 흐름이 없다.
5. **품질 보증·비용 관리 부재.** 단발 `summarize_search` 호출이라 조사 깊이·진행 표시·생성물 검증이 없다.

### 이미 가진 자산 (재사용 핵심)
종합이 필요로 하는 "조사 + 게이트 + 흡수"는 **`research`(맥락 확장 조사)에 이미 구현돼 있다.** 종합은 이를 다중 노드로 일반화하면 된다.
- `expand/research.py` `contextual_research()` — 맥락 고정 웹조사(grounding) → 판정 → 게이트 통과 시 일반 ingest 파이프라인으로 **적재(흡수)**
- `judge_research()` 게이트 — `RELEVANCE_MIN=0.7`, `QUALITY_MIN=0.6` (다의어 오염 방지, fail-closed)
- `_ingest_report_doc()` — 생성 텍스트를 Document로 만들어 `run_ingest`로 적재(맥락 헤더+출처 보존)
- `set_progress_callback`/`emit_progress` + `/research` NDJSON 스트리밍 — 진행 실시간 표시
- 1홉 자동확장·dedup(content_hash/canonical/MinHash)·vault export 등 적재 파이프라인 전체

## 3. 목표 동작 (재설계 플로우)

```
[1] 노드 선별        흥미로운 노드 N개 수집(개선된 UX)
        ↓
[2] 관계성 분석      선택 노드 사이의 구조 파악(공통 이웃·연결 경로·대비)  ← 결정론 + LLM
        ↓
[3] 노드별 맥락 조사  각 노드를 '선택 집합 맥락' 안에서 웹조사 병행(research 재사용, 병렬)
        ↓                                           ↓ 각 조사도 judge 게이트 → 그래프에 흡수
[4] 종합 문서 생성    그래프 지식 + 관계성 + 조사 결과를 묶어 구조화된 문서 합성
        ↓
[5] 검토 & 재흡수    품질/중복/모순 게이트 → 통과 시 'synthesis' 문서로 claire 적재
                     (출처 노드 계보 보존, 원하면 사용자 확인 후)
```

핵심: **[3]의 개별 조사 결과와 [5]의 종합 문서 둘 다 그래프에 흡수**된다. 전자는 사실 보강, 후자는 새 상위 개념 노드 생성.

## 4. 컴포넌트 설계

### 4.1 노드 선별 UX (한계 ④)
- 종합 수집(`synthSet`)을 **검색·경로·문서 패널과 연결**: "검색 결과 전체를 종합에 추가", "경로 상의 노드를 종합에 추가", "이 문서의 노드를 종합에 추가" 버튼.
- 수집 노드를 **그래프에서 시각적으로 표시**(예: 별 표시/테두리) — 현재는 칩만.
- 모바일 대안: 노드 상세의 `➕`만으로 충분히 모을 수 있게(이미 일부 존재) + 수집 패널을 접근 쉽게.
- (열린 질문) 종합 수집과 inspect 선택의 관계 — 현재 분리돼 있음. 유지 vs 통합.

### 4.2 관계성 분석 (한계 ②)
- **결정론 단계**: 선택 노드들의 (a) 직접 관계, (b) 공통 이웃, (c) 쌍별 최단 경로(① 작업의 BFS 재사용), (d) 타입 분포를 추출해 구조화 컨텍스트로.
- **LLM 단계**: 이 구조를 "이들이 어떻게 연결/대비되는가"로 해석하게 해 종합의 뼈대로 삼는다.
- `synthesis_context`를 확장하되 결정론/LLM 분리 유지(테스트 용이).

### 4.3 노드별 맥락 웹조사 (한계 ①) — **직렬 전제로 정정**
- 각 선택 노드에 대해 맥락 고정 웹조사 → 다의어/주제 이탈 방지(research의 강점).
- ⚠️ **"병렬"은 불가**: 모든 Gemini 호출은 `_CALL_LOCK` + `min_interval` throttle로 직렬화된다(`gemini_provider.py:27,107-141`). 스레드로 동시에 띄워도 LLM은 한 번에 하나. 따라서 **직렬 + 진행 스트림**으로 설계하고, 종합당 조사 노드 수를 작게 상한(예: ≤5). wall-clock이 수 분일 수 있음을 UX로 감당(진행 표시·취소).
- ⚠️ `contextual_research`는 **그대로 못 쓴다**: 시그니처가 단일 `node_id`(`research.py:52`)이고 `query`가 필수(74-76). 다중 노드 맥락을 받도록 개조 + **노드별 조사 쿼리 자동 생성**이 필요(현재 없음). 자동 쿼리가 빗나가면 judge relevance 게이트가 전부 보류시킬 수 있어 쿼리 생성 품질이 관건.
- **흡수는 종합 게이트로 단일화(대안2 채택)**: 노드별 조사를 즉시 흡수하지 말고 보고서는 Layer-1 raw로만 보존, 그래프 적재는 §4.5 종합 게이트 한 곳에서만. 게이트 통과 횟수·오염 진입점을 절반으로.
- (비용 통제) 노드 수 상한, "조사 포함/제외" 토글, 실제 호출 수 가시화(§5 R4).

### 4.4 종합 문서 생성 (한계 ⑤ 일부)
- 입력: 그래프 지식(4.1) + 관계성(4.2) + 조사 결과(4.3, 통과·미통과 보고서 포함).
- 출력: **구조화된 마크다운 문서**(render_detail 톤 — 소제목·강조·고유명사 보존, 한국어). 길이/형식은 종합 목적에 맞게.
- 인용/출처 보존: 어떤 노드·조사·문서에서 왔는지 추적 가능하게.

### 4.5 검토 & 재흡수 (한계 ③) — **dedup·extract·게이트 정정**
- **judge는 신규 기능**: `judge_research(query, context, report)`는 인자가 셋뿐, 맥락일치+품질만 본다(`gemini_provider.py:291-307`). "기존 그래프와의 중복/모순"은 그래프 상태를 입력으로 받는 **새 judge**가 필요(=확장 아님). 생성형이라 오염 위험이 커 임계를 research(0.7/0.6)보다 높일지 결정 필요(§7).
- ⚠️ **dedup이 적대적(R1)**: `near_duplicate_document`은 source_type 무관 전체 비교(MinHash 0.90, `db.py:326,331-333`). 종합 문서는 입력 노드 관찰을 많이 포함해 원 문서/이전 종합과 0.90을 넘겨 **"중복" skip**되거나(`pipeline.py:163-169` → `duplicate=True`인데 "흡수했다" 오보), 반복 개선분이 0.90 미만이라 **거의 같은 종합이 누적**된다. → **synthesis 전용 dedup 분기 필수**.
- **extract 여부가 오염을 가른다(대안1)**: 종합을 일반 추출하면 입력 노드와 자동 머지돼 그래프가 왜곡된다. 권장: synthesis는 **추출 생략 + 출처 노드에 명시적 `synthesizes` 관계만** 거는 경량 적재. (열린 결정 §7)
- **증분 종합(대안3)**: 노드집합 정렬 해시를 synthesis의 canonical key로 부여 → 같은 집합 재종합은 새 문서가 아니라 기존을 in-place 갱신(dedup②의 canonical_url 패턴 `pipeline.py:135-158` 재사용). R1의 누적·반복개선을 동시 해결.
- **계보 보존 = 스키마 변경(D)**: `_ingest_report_doc`은 Document에 출처 노드 자리가 없음(`research.py:160-165`). documents 메타/컬럼 추가 + 마이그레이션(`_ensure_column`) 필요 → S 단계 위험 "스키마+마이그레이션"으로 명시.
- **재흡수는 사용자 확인 후**(미리보기 → '흡수' 버튼). 생성형 오염 위험 ↑.
- **트랜잭션 경계(R3)**: 종합 도중 daily-quota 429로 중단되면 부분 상태가 남는다 → 단일 적재 단위로 묶거나 롤백 정책 필요.

## 5. 추가 보완 (설계 검토로 더함)

- **순환/증폭 방지(근거 정정)**: 1홉 자동확장은 `_ingest_report_doc`이 이미 `expand_max=0`을 넘겨 안 일어난다(`research.py:172`) — `onehop:` 게이트가 아니라 이게 담당. 진짜 위험은 **synthesis 노드가 다음 종합의 입력으로 선택돼 정보가 증폭·왜곡**되는 것(코드 게이트 아닌 UX/위상 문제) → synthesis를 별도 위상으로 표시하고 종합 입력에서 기본 제외/경고.
- **중복 종합 감지**: 같은(또는 거의 같은) 노드 집합으로 이미 만든 종합이 있으면 재생성 대신 갱신 제안(MinHash/노드집합 해시).
- **모순 표면화**: 조사 결과가 기존 관찰과 충돌하면 종합 문서에 "상충" 섹션으로 드러내기(은폐 금지 = 정직 협약).
- **반복 개선 루프**: 생성 → 사용자 피드백(부족/방향) → 재생성. 종합은 한 번에 완벽하기 어렵다.
- **부분 실패 내성**: 일부 노드 조사가 rate limit/실패해도 가용분으로 종합 진행 + 무엇이 빠졌는지 명시(`log` 협약: 침묵 절단 금지).
- **비용 가시화(수치 정정 R4)**: `contextual_research` 1회 = research 호출 + judge 호출 **2개**(`research.py:90,103`). 적재가 일어나면 노드당 extract + `render_detail` + 엔티티 임베딩들이 추가(`pipeline.py:222,237`)되어 **노드당 5~10+ 호출**. 종합 1회 실호출 = 관계성1 + 조사노드당(2~10+) + 생성1 + 종합게이트1. 이 실수치 위에서 상한·미리 고지.
- **데이터 보존**: 모든 조사 보고서 원문(통과·미통과 불문)을 Layer-1로 보존(raw 보존 협약) → 알고리즘 바뀌면 재합성 가능.

## 6. 단계적 구현 마일스톤 (제안)

**재배치(검토 반영)**: 가장 비싸고 불확실한 웹조사(구 S2)를 **맨 뒤로** 밀고, 웹조사 없이도 완성되는 "다중 노드 → 문서 → 흡수" 루프를 먼저 세운다(점진 원칙).

| 단계 | 내용 | 의존 | 위험 |
|---|---|---|---|
| **S1** | 관계성 분석(4.2) — `synthesis_context` 확장(결정론 경로 BFS 재사용 + LLM 해석). 기존 종합 즉시 개선, 스키마 무관 | ① 경로 BFS | 낮음 |
| **S2** | 종합 문서 생성(4.4) — `summarize_search` → 구조화 생성 프롬프트로 교체. **조사 없이 그래프 지식만으로** | S1 | 낮음~중 |
| **S3** | 재흡수 루프(4.5) — **synthesis 전용 dedup 분기(R1) + extract 생략/`synthesizes` 관계(대안1) + 증분 canonical key(대안3) + 계보 메타(스키마+마이그레이션) + 사용자 확인 흡수**. 여기서 "다중→문서→흡수" 완성·검증 | S2, 스키마 | **높음** |
| **S4** | 선별 UX(4.1) — 검색/경로/문서→종합 연결, 그래프 표시. 독립적이라 언제든 | — | 낮음 |
| **S5** | 노드별 웹조사(4.3) — **직렬 + 진행 스트림**, 다중맥락 개조 + 쿼리 자동생성, 종합 게이트로 단일 흡수. 가장 비싸고 위험 → 마지막 옵션 | S3, research | **높음** |

각 단계는 검증(단위 + 로컬 mock + Playwright)까지 끝낸 뒤 다음으로(빅뱅 금지, GOALS 원칙). **S1+S2+S3만으로 핵심 가치(다중 노드 종합·흡수) 완성** — S5(웹조사)는 가치 대비 위험이 커 별도 판단.

## 7. 열린 결정 사항 (사용자 상의 필요)

1. **재흡수 방식**: 자동 적재 vs 미리보기 후 '흡수' 버튼(권장). 생성형이라 오염 위험 ↑.
2. **조사 비용 상한**: 종합당 조사할 노드 수 상한(예: 최대 5) / "조사 포함" 토글 기본값.
3. **synthesis 노드의 그래프 내 위상**: 일반 엔티티처럼 둘지, 별도 타입/색으로 구분할지(증폭 방지·역추적과 연결).
4. **선별 UX 범위**: 어디까지(검색→종합, 경로→종합, 문서→종합) 우선순위.
5. **종합 결과물 형태**: 그래프 적재 외에 vault(옵시디언) 노트로도 export 할지.
6. **(핵심) 종합 문서를 extract(엔티티 추출)할 것인가?** — 추출하면 입력 노드와 머지돼 그래프 오염. 경량 적재(추출 생략 + `synthesizes` 관계)가 대안. 오염 여부를 가르는 가장 중요한 결정(대안1).
7. **조사 직렬화 수용 vs RPM 상향** — 직렬이라 wall-clock 수 분. UX로 감당할지, `min_interval`/RPM을 올릴지(daily quota 소진 위험↑).
8. **재종합 canonical key 정의** — 노드집합 해시 정규화(순서·부분집합 처리).
9. **daily-quota 중단 시 일관성 정책** — 부분 흡수된 조사를 남길지/롤백할지(R3).
10. **synthesis judge 임계값** — research는 0.7/0.6. 생성형 오염 위험이 더 크니 별도(더 높은) 임계 둘지.

## 9. Advisor 검토 핵심 (2026-06-24, 코드 근거)

초안의 "재사용 자산" 가정 중 두 개가 실제 코드 제약에 막혔고, 근거 하나가 틀렸다. 본문은 정정 반영했으며, 구현 착수 전 반드시 기억할 사실:

- **(A) 병렬 조사 무효**: Gemini 호출은 `_CALL_LOCK` + throttle로 프로세스 전역 직렬(`gemini_provider.py:27,107-141`). 진행 콜백은 thread-local(`provider.py:76`), `contextual_research`는 자체 conn 생성(`research.py:80`) → 동시 스레드는 LLM 직렬 + write 경합. **직렬로 재설계**.
- **(B) `contextual_research` 개조 필요**: 단일 `node_id`·필수 `query`(`research.py:52,74`). 다중 맥락 + 쿼리 자동생성 필요.
- **(C) 중복/모순 judge는 신규**: `judge_research`는 그래프 상태 미입력(`gemini_provider.py:291`).
- **(R1) dedup 적대적**: `near_duplicate_document` 전체 비교 MinHash 0.90(`db.py:326`) → 종합이 skip되거나 누적. **synthesis 전용 분기 필수**.
- **(R2) 순환방지 근거 정정**: `expand_max=0`이 담당(`research.py:172`), `onehop:` 게이트 아님.
- **(R3) 트랜잭션 경계 부재**: daily-quota 429 즉시 raise(`gemini_provider.py:130`) → 부분 흡수 잔존.
- **(R4) 비용 과소**: 노드당 5~10+ 호출(research+judge+extract+detail+embed).
- **채택한 대안**: ①synthesis는 extract 생략 + `synthesizes` 관계만(오염 방지) ②조사는 종합 게이트로 단일 흡수(진입점 절반) ③증분 종합(노드집합 canonical key로 in-place 갱신).
- **마일스톤 재배치**: 웹조사를 맨 뒤로(S5), S1~S3로 핵심 루프 먼저 완성.

전체 검토 원문은 이 작업 세션 기록 참조.
