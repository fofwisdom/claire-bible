[#sec-overview]
== 개요: VCF 9.x 운영 패러다임의 전환

과거 가상화 및 클라우드 인프라 운영 환경에서는 성능 지표, 로그, 네트워크 흐름 분석 도구가 개별 어플라이언스로 파편화되어 존재하였다. 엔지니어는 시스템 장애나 성능 저하가 발생했을 때 여러 개의 브라우저 탭과 콘솔 창을 오가며 개별 타임스탬프를 수작업으로 대조하고, 대상 가상 머신에 SSH로 접속해 원인을 규명해야 하는 운영상 비효율을 겪었다. 대표적으로 Aria Operations(구 vRealize Operations)와 Aria Operations for Logs(구 VMware vRealize Log Insight)가 각각 독립적인 가상 어플라이언스로 배포·관리되면서 제품별 라이프사이클 관리(LCM)와 사용자 인터페이스의 단절이 지속되었다.

[quote, VCF Operations 아키텍처 비전]
VCF 9.0 및 9.1에서는 파편화된 운영 도구를 단일 글로벌 콘솔로 수렴(Convergence)하여 지표(Metrics), 로그(Logs), 네트워크 플로우(Flows)를 단일 컨텍스트 안에서 상호 연관 분석할 수 있는 체계를 완성한다.

VMware Cloud Foundation(이하 VCF) 9.1부터 로그 관리는 독립형 어플라이언스 형태를 탈피하고, #VCF Management Services(VMSP) 상에서 마이크로서비스로 구동되는 통합 기능#으로 전면 재편되었다. 이를 통해 운영자는 복수의 콘솔을 전환할 필요 없이 단일 화면에서 인프라 전반의 텔레메트리 데이터를 분석하고 문제 해결 시간(Mean Time To Resolution, MTTR)을 획기적으로 단축할 수 있다.

'''

[#sec-architecture]
== 차세대 로그 아키텍처 및 성능 확장성

=== 마이크로서비스 기반 내부 아키텍처

VCF 9.1의 로그 관리 시스템은 VCF 관리 도메인(Management Domain) 내부의 VCF Management Services 플랫폼 위에 마이크로서비스 형태로 상주한다. 내부 아키텍처는 크게 세 가지 핵심 컴포넌트로 구성된다:

* *Envoy Gateway*: 외부 에이전트 및 시스템으로부터 유입되는 모든 API 요청 및 로그 수집 트래픽의 수신, 로드 밸런싱, 라우팅을 총괄하는 인프라 게이트웨이 역할을 수행한다.
* *Custom Log Processor*: 인입되는 로그 스트림의 파싱, 토큰화(Tokenization), 필터링, 마스킹 규칙 적용 및 데이터 정형화를 담당하는 엔진이다.
* *OpenSearch 백엔드*: 대규모 분산 검색 및 분석 엔진으로 기능하며, 고속 인덱싱과 다차원 쿼리 성능을 제공한다.

=== 확장성 및 성능 지표 비교

백엔드 엔진의 OpenSearch 전환과 파이프라인 최적화에 힘입어 수집량 및 스토리지 수용량이 전작 대비 대폭 향상되었다.

.VCF 로그 아키텍처 성능 지표 변화
[cols="1,1,1", options="header"]
|===
|성능 및 용량 지표 |이전 릴리스(Aria Operations for Logs 8.x) |VCF Operations 9.1 (통합 로그 엔진)

수집량 측면에서 초당 약 stem:[1.14 \times 10^6]개에 달하는 이벤트를 유실 없이 병렬 처리할 수 있으며, 클러스터 스토리지 수용량이 171 TB까지 확장되어 엔터프라이즈급 대규모 플릿(Fleet) 환경에서도 안정적인 텔레메트리 수집 인프라를 유지한다.

=== 플릿(Fleet) 단위 배포 토폴로지

VCF 9.1에서 로그 관리는 단일 클러스터 범위에 국한되지 않고, 전체 VCF 플릿 전반에 서비스를 제공하는 글로벌 아키텍처를 취한다.

* 중앙 관리 도메인(Management Domain)의 VCF Operations 내부에 로그 코어 서비스가 상주한다.
* 복수의 VCF 인스턴스(VCF Instance 1, VCF Instance 2 등)와 각 인스턴스 소속의 워크로드 도메인(Workload Domain), 공유 NSX Manager, vCenter 클러스터들이 중앙의 로그 수집 파이프라인으로 직접 연동된다.
* 개별 엔드포인트 간 통신 프로토콜로는 기존 Syslog 및 CFAPI(Cloud Foundry API / Custom Flow API), JSON API가 완벽하게 하위 호환되며, Cloud Proxy 기반 포워더와 8.x 인스턴스로부터의 로그 전달도 연속적으로 지원된다.

'''

[IMPORTANT]
그린필드(신규) 배포 시 지정하는 로그 관리 인스턴스의 FQDN은 기존 시스템에서 사용하던 구 FQDN과 중복되지 않도록 *새로운 FQDN(New FQDN)*을 지정해야 한다. 이전 FQDN을 그대로 재사용하여 발생하는 서비스 등록 장애 및 SR(Service Request) 발생 사례가 다수 보고되었으므로 네트워크 사전 검증이 필수적이다. 또한 Day 2 구성 작업 시에는 사전에 계획된 유지보수 시간(Maintenance Window)을 확보해야 한다.

=== 통합 수집 활성화 및 구성 관리

로그 관리 서비스 설치가 완료되면 `Operate -> Administration -> Integrations` 메뉴에서 실제 모니터링 대상 계정의 수집을 켜야 한다.

1. 관리 도메인 및 워크로드 도메인 소속의 각 vCenter Server 인스턴스를 선택한다.
2. `Log Operation` 항목의 `#Activate Log Collection#` 체크박스를 명시적으로 활성화한다.
3. NSX 인스턴스에 진입하여 동일하게 `Activate Log Collection` 옵션을 활성화한다.

[NOTE]
로그 서비스가 정상 설치되어 구동 중임에도 로그 화면에 데이터가 인입되지 않는 현상은 대다수 해당 체크박스가 비활성화되어 발생한다. 구성 관리 페이지에서 각 인스턴스별 수집 활성화 여부를 반드시 확인해야 한다.

[#sec-core-pillars]
== 로그 관리의 3대 핵심 기둥

VCF Operations의 통합 로그 아키텍처는 다음 3대 운영 영역을 체계적으로 지원한다.

* *모니터링(Monitor)*: 특정 로그 패턴의 출현 여부 또는 결손 상태를 실시간 탐지하고 대시보드로 시각화하여 잠재 위험을 감지한다.
* *진단 및 장애 분석(Troubleshoot)*: 개별 로그 이벤트를 의미론적 단위로 집약하고 지표 및 플로우와 교차 분석하여 근본 원인을 파악한다.
* *보안 운영(SecOps)*: VCF 전반의 감사 추적(Audit Trail), 세분화된 접근 제어(RBAC), 규제 준수용 아카이빙을 총괄한다.

=== 1. 모니터링 및 복합 알림 체계

VCF 9.1은 모든 VCF 스택 컴포넌트(vCenter, ESXi, NSX 등)에서 생성되는 로그의 수집 포맷과 타임스탬프를 일관된 표준 규격으로 정규화한다. 정규화된 로그 스트림은 성능 지표와 결합되어 강력한 복합 경보(Combined Alert)를 생성한다.

* *로그 부재 및 출현 경보*: 장애 발생 시 특정 오류 문자열의 급증뿐만 아니라, 주기적으로 도달해야 하는 하트비트 로그의 중단을 즉각 포착한다.
* *증상-지표 상관 결합*: CPU 스파이크, IOPS 지연과 같은 성능 지표 이상 징후에 로그 에러 패턴을 단일 알림 규칙으로 묶어 경보 노이즈(Alert Fatigue)를 줄이고 정확한 판단 근거를 운영팀에 전달한다.

=== 2. 문제 해결 및 워크벤치(Workbench) 통합 분석

통합 워크벤치는 장애 분석 세션을 생성하여 단일 컨텍스트 윈도우에서 인프라의 모든 텔레메트리를 다각도로 검토할 수 있도록 지원한다.

* *다차원 상관분석*: 동일 타임스탬프 상에서 CPU, 메모리, 스토리지 IO 지표와 로그 이벤트, 네트워크 흐름(Flow) 정보를 횡단 추적한다.
* *병렬 로그 비교(Log Compare)*: 최대 4개의 독립 쿼리를 동시에 실행하여 시스템 변경 전후의 상태를 대조 분석할 수 있다. 예를 들어 패치 적용 전일과 적용 당일의 네트워크 로그를 대조하거나 서로 다른 두 호스트 간의 동작 차이를 시각적 스택 차트(Stacked Chart)로 확인할 수 있다.

=== 3. 보안 운영, 거버넌스 및 규제 준수

보안 운영 측면에서는 내부 보안 감사와 컴플라이언스 대응을 위한 데이터 보호 기능이 대폭 강화되었다.

* *로그 데이터셋(Log Datasets) 및 스코프 기반 RBAC*:
+
특정 테넌트나 업무 조직(예: NSX 네트워크팀)이 타 시스템(vCenter, 일반 애플리케이션 등)의 로그에 접근하지 못하도록 통제한다. 로그 메시지 자체에 대상 객체명이 누락되어 있더라도 태그, 호스트, 애플리케이션 이름을 기반으로 동적 데이터셋을 정의하고 이를 사용자 권한(RBAC Roles)과 매핑하여 내부자 위협 및 권한 오남용을 억제한다.

* *인메모리 로그 마스킹 및 필터링(Masking & Filtering)*:
+
PCI DSS, HIPAA, GDPR 등 규제 준수를 위해 신용카드 번호(PAN), 주민등록번호(SSN), 개인식별정보(PII)를 정규표현식(Regex) 기반으로 실시간 탐지하여 해시 또는 마스킹 처리한 후 저장소에 기록한다.

* *수명 주기 및 파티션별 보존(Partitioning & Archival)*:
+
로그 파티션별로 독립적인 보존 기간(Retention Period)을 구성할 수 있다. 운영 로그는 단기 보존 정책을 적용하고, SOX 규정 등 최대 7년 이상의 장기 보관이 요구되는 로그는 외부 S3 호환 스토리지(MinIO 등) 또는 NFS 엔드포인트로 자동 아카이빙하도록 지정할 수 있다.

'''

[#sec-advanced-features]
== 고급 운영 기능 상세

=== 필드 라이브러리(Field Library)와 토큰화 인덱싱

VCF 9.1에는 검색 성능을 극대화할 수 있는 필드 라이브러리 거버넌스 체계가 도입되었다.

* *시스템 정의 필드 vs 시스템 발견 필드*: 시스템이 사전에 정의한 핵심 필드는 자동 인덱싱 처리되나, 런타임에 동적으로 발견된 비정형 필드는 기본적으로 비인덱스(Non-indexed) 상태로 유지된다.
* *인덱싱 승격(Upgrade to Index)*: 관리자는 자주 검색하거나 대시보드 집계에 사용하는 커스텀 필드를 수동으로 인덱싱 필드로 승격시킬 수 있다. 데이터베이스 내부에서 해당 필드가 토큰화되어 쿼리 응답 속도가 비약적으로 개선된다.
* *SDCompID 필터*: VCF 전용 컴포넌트 식별자로 새롭게 추가된 내장 필터다. 예를 들어 `SDCompID contains NSX` 쿼리를 사용하면 복잡한 호스트명 지정 없이도 NSX 관련 모든 수집 로그를 즉각 격리 추출할 수 있다.

=== 아카이브 로그 임포트(Archive Log Import) 및 능동 대조

과거 장기 스토리지로 내보낸 아카이브 로그는 단순 백업 보관에 그치지 않고 사후 감사 및 침해 사고 조사를 위해 시스템 내부로 재유입시킬 수 있다.

1. 외부 S3(MinIO) 또는 NFS 스토리지에 저장된 경로와 수집 일시 범위를 지정하여 `Log Import` 작업을 실행한다.
2. 시스템은 가져온 데이터를 별도의 임시 파티션(`Import Archive -> Archived Logs`)에 배치한다.
3. 운영자는 `Log Compare` 기능을 통해 현재 시스템에서 수집 중인 #활성 로그(Active Logs)와 아카이브에서 불러온 과거 로그(Archived Logs)를 단일 인터페이스에서 직접 맞비교#하여 패치 이전의 정상 패턴과 현재의 변칙 패턴을 정밀 검증할 수 있다.

=== 통합 에이전트 및 보안 수집 구성

로그 에이전트 관리는 VCF Operations 콘솔로 완전히 통합되었다.

* *멀티 에이전트 생태계*: 기본 vCenter 및 NSX 내장 로깅 외에도 Fluent Bit, Fluentd 에이전트로부터의 로그 포워딩을 기본 지원한다.
* *비밀키(Secrets) 인증*: 신규 가상 머신에 로그 수집 에이전트를 설치할 때 발급된 인증 시크릿 토큰을 에이전트 환경 설정 파일(INI 등)에 입력하여 상호 신뢰 통신을 수립한다.
* *강제 SSL 암호화*: Syslog 인입 및 API 로그 수집 엔드포인트에 대해 전송 구간 SSL 암호화를 강제 적용할 수 있어 전송 중 패킷 스니핑을 방지한다.
* *자체 헬스 모니터링*: `Log Management Health Overview` 전용 대시보드를 제공하여 로그 서비스 자체의 인입률, 오픈 경보, 이벤트 소모율, 리소스 가용성을 상시 감시한다.
